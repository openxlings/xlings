## 1. `xlings info` 的 2.4 秒

### 1.1 实测

```
xlings config       0.04 s
xlings search gcc   0.06 s     ← 同样加载索引
xlings list gcc     0.82 s
xlings info gcc     2.37 s
```

`real 2.377s / user 2.357s / sys 0.019s` —— **没有 I/O 等待,全是计算**。

且与被查的包**无关**:

| 包 | 配方行数 | 耗时 |
|---|---|---|
| gcc | 576 | 2.38 s |
| proot | 60 | 2.39 s |
| node | — | 2.37 s |
| mcpp-short-cmd | — | 2.38 s |

一个与查询内容无关的**常量开销**。`search` 走同一个 `get_catalog(LocalOnly)` 却只要 0.06s,所以代价不在索引。

### 1.2 热点(gdb 采样)

```
coordinate_from_payload_path        ← std::views::split,每个路径组件构造一个 std::string
  ← shallow_owner_candidates_for
  ← build_owner_coordinates
  ← assemble_inventory
```

规模:这个 home 有 **1312 个包 / 1808 条版本记录**。`info` 为了回答末尾那两行

```
bindings: xim-aarch64-musl-gnu-gcc, xim-gnu-gcc -> 16.1.0, xim-musl-gnu-gcc
subos: default, dev-hello, gfxbuild, mcpp-test
```

装配了**完整清单**,而每条记录都要把 payload 路径切成组件、逐个构造 `std::string`,再从后往前找 `xpkgs`。1808 次 × 每次约 8 个组件 = 约 1.5 万次堆分配加比较,只为得到两个字段(`ns`/`package`/`version`)。

### 1.3 方案

三层,按收益/风险排序:

**A. 让 `coordinate_from_payload_path` 不分配。** 它要的只是"最后一个 `xpkgs` 之后的两段"。用 `string_view` 从右往左扫,零 `std::string` 构造。这是纯局部优化,不改语义,单测可逐字节比对新旧结果。

**B. `info` 不该装配完整清单。** 它要的是"哪些 subos 引用了**这一个** target"。`assemble_inventory` 是为 `list`/`doctor` 那种全量视图写的;`info` 应当走一个按 target 过滤的窄路径 —— 即先筛出该 target 的版本记录(1808 → 通常个位数),再只对它们求 owner。

**C. 缓存 payload→坐标 的映射。** 只在一次进程内多次装配时有收益,`info` 是单次,所以**不做** —— 记在这里是为了说明为什么不做。

预期:A 单独可能把 2.4s 降到亚秒;A+B 应当进入与 `search` 同一量级(<0.1s)。**这两个数字是预期,不是承诺**;实施时按 §1.4 实测。

### 1.4 验证方式

不能只测 `info gcc` 变快了 —— 那无法区分"变快"和"少做了事"。必须:

1. 同一个 home 上,新旧二进制的 `info` **输出逐字节相同**(含 `bindings` 与 `subos` 两行)
2. `list` / `doctor` / `remove` 三条同样使用 `assemble_inventory` 的路径输出不变
3. 计时在**同一个 home**(1312 包)上做,并记录包数 —— 在空 home 上测会得到一个没有意义的数字

## 2. i18n 覆盖

### 2.1 现状:覆盖了顶层,漏掉了全部子命令

2026.8.22.3 翻译的是 `ui/banner.cpp` 里**手写的顶层命令表**。而 `xlings subos -h` 的内容来自 `src/cli/spec.cpp`,那里一条也没接:

```
  xlings subos
  Manage SubOS environments        ← 未翻译

  用法                             ← 已翻译(章节标题)
    xlings subos [SUBCOMMAND]

  子命令                           ← 已翻译
    new     Create a SubOS         ← 未翻译
    use     Enter a SubOS          ← 未翻译
```

章节标题是中文而内容是英文,比全英文更难读 —— 它让人以为翻译坏了。

### 2.2 未覆盖的量(实测)

| 来源 | 条数 | 内容 |
|---|---|---|
| `src/cli/spec.cpp` | **110** | 全部子命令、参数、选项的描述 |
| `src/cli.cpp` 的 `.description()` / `.help()` | **49** | 同上,注册时的另一份 |
| `src/ui/*.cpp` 字面量 | 4 | 面板表头等 |
| **合计** | **163** | |

已覆盖约 40 条。**目标不小于 100 处**是合理的 —— 单是 spec.cpp 的 110 条就超过了,不需要为了凑数去翻译不该翻译的东西。

### 2.3 一个必须先解决的结构问题

`spec.cpp` 与 `cli.cpp` **各存了一份命令描述**,而且它们必须一致(CI 有一条 "cli spec parity" 检查在盯)。翻译时若只改一处,parity 检查会红;两处都改则等于把同一段文案维护两遍。

所以顺序是:**先合并成一处**,再接 i18n。合并方向是 `spec.cpp` 作为唯一来源,`cli.cpp` 注册时从它取描述 —— spec 已经是被 parity 检查认定的权威。

### 2.4 覆盖范围与判据

判据不变:**能敲进终端的东西不翻,解释它的话翻。**

| 类别 | 数量 | 翻译? | 说明 |
|---|---|---|---|
| 章节标题(`USAGE`/`SUBCOMMANDS`/`OPTIONS`/`ARGS`) | 5 | ✅ 已完成 | |
| 顶层命令描述 | 12 | ✅ 已完成 | |
| 全局选项描述 | 4 | ✅ 已完成 | |
| `config` 字段标签 | 11 | ✅ 已完成 | |
| **子命令描述**(`subos new` / `use` / `list` …) | ~35 | ❌ 待做 | §2.2 的主体 |
| **子命令选项描述**(`--storage` / `--sandbox` …) | ~55 | ❌ 待做 | |
| **位置参数描述**(`SubOS name` / `Package names` …) | ~20 | ❌ 待做 | |
| **交互提示语**(`Which theme ?` / `Select a package:`) | 8 | ❌ 待做 | 见 §3;**交互本身也要 i18n** |
| **面板表头**(`Sub-OS environments:` / `Installed packages`) | ~12 | ❌ 待做 | `subos use` 的列表就在这里 |
| 命令名、旗标名、占位符、环境变量名 | — | ❌ 永不翻译 | `install` / `--yes` / `<version>` / `XLINGS_HOME` |
| `std::format` 的参数(版本号/路径/包名) | — | ❌ 永不翻译 | 翻译数据会让复制出来的命令失效 |
| `log::debug`(106 处) | 106 | ❌ 不翻译 | 读者是开发者与 issue 报告,英文更利检索 |

待做合计 **约 130 处**。

## 3. 交互覆盖

### 3.1 现状:8 处

| # | 位置 | 状态 |
|---|---|---|
| 1 | `use <name>` 版本选择 | ✅ |
| 2–4 | `install` / `remove` / `update` 确认 | ✅ |
| 5–7 | `self install` 的三处确认 | ✅ |
| 8 | `install <模糊名>` 包名消歧 | ✅ |
| 9–13 | `config --lang/--mirror/--theme/--ui-mode/--interactive` 缺值 | ⏳ 本轮已实现,待发布 |

### 3.2 缺口的共同形状

用户报的 `xlings subos use` 是典型:

```
$ xlings subos use
  Sub-OS environments:
    agent-influence  (…)
    ...45 个...
```

**列出 45 个,然后要求用户把其中一个重打一遍** —— 而且这段列表还没有 i18n。凡是这个形状的地方,交互都该覆盖。

### 3.3 建议覆盖到 31 处

| # | 决策点 | 候选来源 | 现状 | 优先级 |
|---|---|---|---|---|
| 1 | `use <name>` 版本 | 当前 subos 已装版本 | ✅ | — |
| 2–4 | install / remove / update 确认 | y/n | ✅ | — |
| 5–7 | `self install` 三处确认 | y/n | ✅ | — |
| 8 | `install <模糊名>` 消歧 | 模糊匹配前 5 | ✅ | — |
| 9–13 | `config` 五个枚举设置缺值 | 各自枚举 | ⏳ | — |
| **14** | **`subos use` 无参** | 全部 subos | ❌ | **高**(用户已报) |
| **15** | `subos remove` 无参 | 全部 subos | ❌ | 高(破坏性,更需要看清再选) |
| **16** | `subos info` 无参 | 全部 subos | ❌ | 中 |
| **17** | `use <name>` 的 shim 版本(`no_active_version`) | 已 opt-in 的版本 | ❌ | 高 |
| **18** | `remove <name>` 有多个 subos 引用时 | 引用它的 subos | ❌ | 中 |
| **19** | `info <name>` 名字模糊时 | 模糊匹配 | ❌ | 中 |
| **20** | `why <pkg> <dep>` 的 dep 缺省 | 该包的依赖 | ❌ | 低 |
| **21** | `update <pkg>` 无参 | 可更新的包 | ❌ | 中 |
| **22** | `subos new --from` 无值 | 全部 subos | ❌ | 低 |
| **23** | `subos new --storage` 无值 | shared/tmpfs/image | ❌ | 低 |
| **24** | `subos new --runtime` 无值 | 已装 runtime | ❌ | 低 |
| **25** | `list <filter>` 无匹配时 | 近似名 | ❌ | 低 |
| **26** | `search` 结果直接选中安装 | 搜索结果 | ❌ | 中 |
| **27** | `config --index-repo` 移除哪一个 | 已配置的 repo | ❌ | 低 |
| **28** | `self doctor --fix` 逐项确认 | 每个 finding | ❌ | 中 |
| **29** | `remove` 有依赖者时的 `--force` 确认 | y/n | ❌ | 中 |
| **30** | `install` 跨 subos 时选目标 subos | 全部 subos | ❌ | 低 |
| **31** | 首次运行的引导(语言/镜像) | 各自枚举 | ❌ | **不做,见下** |

**第 31 项建议不做**,理由与之前一致:首次运行时用户还没有判断依据,探测优于提问。列出来是为了说明它被考虑过并被否决,而不是遗漏。

**如果实施时发现某项不成立,必须在实施记录里写明为什么**,而不是静默从表里去掉 —— 这份表是承诺,不是愿望。

### 3.4 三条约束(不变)

1. 交互只能替换"重打一遍",不能是唯一路径
2. 回落必须是完整答案,不是错误
3. 确认层看 `stdin` 且脱离 `tui.interactive`;选择层额外要求它

### 3.5 交互提示语必须走 i18n

现有 8 处提示语全是硬编码英文(`Which {} ?` / `Multiple matches found. Select a package:` / `Remove {} from subos '{}' ?`)。扩到 31 处会变成 31 条硬编码英文。

**因此 §2 的 i18n 接线必须先于或同步于 §3 的扩展**,否则每加一个交互点就多一条要回头翻译的字符串。提示语的 msgid 用 `PromptEvent::id`(已存在、稳定、唯一),与诊断用 `diag.code` 同构。

## 4. 选择器重做

### 4.1 现状与问题

```
╭────────────────────────────────────────────╮
│ Which mirror ?                             │
├────────────────────────────────────────────┤
│ > CN                                       │
├────────────────────────────────────────────┤
│ ↑↓ navigate  Enter select  Esc cancel      │
╰────────────────────────────────────────────╯
```

两个问题:

**其一,配色。** 六处边框全部使用 `theme::border()`,深色主题下是 `#334155`(slate-700)。在深色背景(`#0D1117`)上对比度约 **1.6:1**,远低于可读下限。边框、分隔线、提示行都是这个颜色,于是整个框"糊"在背景里。

**其二,形态。** 一个带圆角边框、上下分隔线、底部提示行的**盒子**,为了从 2 个选项里选 1 个要占 6 行。它与 xlings 其余输出(左对齐、无框、`◆`/`▸` 前缀)也不是一套视觉语言。

### 4.2 形态方案 —— 需要你裁决

**建议:内联列表,无框。**

```
  ◆ Which mirror ?
  ▸ CN                          (current)
    GLOBAL

    ↑↓ move   enter select   esc cancel
```

- 与 `xlings subos` / `xlings list` 的既有输出同一套语言(`◆` 标题、`▸` 当前项)
- 2 个选项占 5 行而不是 6;10 个选项占 13 行而不是 14,且没有边框宽度限制
- 选中项用 `accent` 而非反色块;当前值用 `muted` 标注 `(current)`
- 底部提示行保留但降为 `muted`,且**只在首次出现**(复用已有的 `hint_seen` 机制)

**配色修正**(与形态无关,两案都要):

| 用途 | 现在 | 改为 | 理由 |
|---|---|---|---|
| 选中项 | 反色块 | `accent` 前景 + `▸` | 反色块在窄终端里会撑满整行,视觉噪声大 |
| 未选项 | `text` | `text` | 不变 |
| 提示行 | `border` | `muted` | `muted` 深色下是 `#94A3B8`,对比度约 7:1 |
| 分隔/边框 | `border` | 取消 | 无框则不需要 |

`border` 槽本身**不改** —— 它在面板场景下是合适的;问题是选择器把它用在了需要可读性的地方。

**备选案(若你更想保留框):** 保留 `borderRounded`,但边框改用 `muted`,提示行改用 `muted`,选中项改 `accent`。改动更小,视觉语言仍与其余输出不一致。

### 4.3 验证

选择器是 TUI,自动化断言只能覆盖行为不能覆盖观感。可测的部分:

1. pty 下方向键 + 回车 → 选中项被写入(已有 N9 的模式)
2. `esc` → 取消,退出码 0,状态不变
3. 非交互 → 完全不渲染,回落到列表
4. `XLINGS_TERM_WIDTH=40` 下不换行错乱
5. **对比度**:取渲染后的 SGR 前景色与背景色,计算 WCAG 对比度并断言 ≥ 4.5:1 —— 这条能自动化,且正是现在会失败的那条
