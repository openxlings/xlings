## 1. Changes

| Item | Change |
|---|---|
| Install configures once per scope (#632 §1) | Each scope's `.xlings.json` records `configured: {"<ns>:<name>@<version>": <revision>}` (a top-level sibling of `workspace`). A present, current payload whose record matches the recipe's revision, and whose ledger entries are all claimed by the scope's `installed[]`, is not configured again. An install whose whole closure is in that state does the report, the activation and one routing-table rebuild, and says how to configure again. `install --reconfig` (interface: `"reconfig": true`) runs config for the whole plan, as every install did before. No record means "configure": a home from before this version configures once per package and records it |
| Revision reaches every scope | A revision bump reinstalls the shared payload in the scope that meets it first; every other scope's record then names the old revision, so its next install configures again. `remove` and an unbind take the record with the binding |
| Progress per node (#632 §1) | In the default mode an install prints `  [i/n] installed <coord>` or `  [i/n] configured <coord>` for each node that did something; the interface gets the same as `progress` events with phase `configure` (protocol 1.4) |
| Privileged env notice (#632 §4) | The warning for an env declaration that can load our code into other processes is printed when the declaration is new or changed in its binding's section, not on every re-record |
| Routing-table rebuild cost | A rebuild parsed the whole home config (3.6 MB on a measured home) to read `knownProjects`, and in project scope rewrote it to move `lastSeen`. The list is now taken from the parses that already happen and re-read only when the file's size or mtime changed; `lastSeen` is written at most once a day per project. The rebuild itself stays per node: later hooks of the same plan run earlier nodes' commands by name (gcc's config runs `<bindir>/gcc-specs-config`) |
| Index build output (#629) | libxpkg 0.0.59 hands a `pkgindex-build.lua`'s `io.write`/`print` to xlings instead of fd 1. Off a terminal and on one, a finished build prints `[index] built <ns> (<n> files)` once; the script's other lines are passed on; the interface's `index_rebuild` progress events are unchanged |
| No bar for index artifacts | An `index:<name>` download never draws frames, on any destination; its start and finish lines remain |
| Blank line after a progress block | On a terminal, the last frame of a download block is followed by one blank line |
| One answer to "may this run redraw" | The download renderer asks the frontend's capability (`--ui-mode cli`, `--agent`, the terminal) instead of a predicate that ignored the UI mode. `--ui-mode cli` on a terminal therefore prints download start/finish lines instead of bars |
| `self update` | Runs its two child commands with `--ui-mode cli`: no progress bars inside the update's narrative |
| elfpatch (libxpkg 0.0.59, libxpkg#43) | The automatic patch leaves alone a file with neither PT_INTERP nor DT_NEEDED (static, static-pie, a loader), a file built for another machine than the loader being written, and anything a recipe lists in `elfpatch.set{ skip = ... }`; `set{ scan = ... }` narrows the walk |
| Doctor remedy | `SubosRuntimeUnknown` prints `xlings install glibc --reconfig` |

## 2. Client-visible differences

- `xlings install <pkg>` of something installed and configured here takes the
  time of a plan (a measured 89-node closure spent ~85 s re-running config
  before) and prints one line pointing at `--reconfig`.
- Repairing a scope's links or env sections by hand-running `install` now needs
  `--reconfig` (or `self doctor --fix`).
- Interface protocol 1.4: `install_packages` accepts `reconfig`; `progress`
  events with phase `configure` appear during installs.
- `--ui-mode cli` on a terminal no longer draws download bars.
- `install --use` / `update` still activate the requested package (through
  `use`), but no longer re-activate a dependency that is already configured in
  the scope: that re-activation was a side effect of re-running every node's
  config with `--use`, and it overrode a version the user had selected with
  `xlings use`. A dependency installed or configured by the run is activated as
  before.
- `xlings update` into a file or a pipe carries no `\r` and no escape sequence
  from index build scripts.
