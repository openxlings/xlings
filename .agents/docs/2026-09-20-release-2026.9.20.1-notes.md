## 3. 发布链上真正踩到的问题

### 3.1 `verify-release.sh` 全绿 ≠ 客户端能装到

`release.yml` 的 `publish-index` 跑在 `bump-index` 的 PR **被合并之前**,
所以客户端真正抓的那个索引产物里,`latest` 还是旧版本。结果:

```
[xlings] installing xlings@latest...
xim:xlings@2026.9.16.1 is already installed      ← exit 0,什么都没升
```

**这不是 xlings 的 bug**:它正确地装了 `latest` 解析出来的东西,而索引当时确实说
`latest = 2026.9.16.1`。`verify-release.sh` 之所以全绿,是因为它读的是 **git main**,
而 git main 从合并那一刻起就是对的。**缺口在 git main 与已发布指针之间。**

合并 `#864` 之后索引仓的 `Publish Index Artifact` 会重新发布(rolling `latest` +
内容哈希 `vda8a683`),并在 **13:05** 推送 pointer。我前两次 `self update` 正好撞在
这个推送上。第三次成功。

> **下次的做法**:发布后不要只看 `verify-release.sh`。再加一步 ——
> **像客户端那样解析一次 `latest`**(`xlings update` 之后读
> `~/.xlings/data/xim-pkgindex/pkgs/x/xlings.lua`),确认指针已经推完。
> 顺序本身也值得改:让 `publish-index` 依赖 `bump-index` 的合并,而不是与之并行。

### 3.2 #602 的修复对「升进来的这一跳」不生效

升级 **into** 2026.9.20.1 这一跳是由**旧的 2026.9.16.1 二进制**执行的,它没有 `--use`,
所以仍然打印了:

```
xim:xlings@2026.9.20.1 installed, but 'xlings' still resolves to 2026.9.16.1 — ...
```

发布出去的二进制里确认带着修复(`strings` 能看到
`xlings install xlings@latest -y --use`),所以**从这一版往后**不再出现。
这是这类「自升级」修复的固有性质,不是回归。

## 4. 实现期间被实测推翻的判断

按发现顺序。每一条都是**先写对了代码、测试也全过**,靠核对陈述才发现的。

1. **「CLI 上没有 `--use`,要新增」** —— 早就有(`cli.cpp` install 子命令 `-u/--use`)。
2. **「glibc 2.39 的 recipe 没调用 `relocate_build_paths`,要改索引仓」** —— 已经调用了。
   实测:全新安装 `glibc@2.39` 产出的 `ldd` 是**好的**(RTLDLIST 完整、TEXTDOMAINDIR 已重定位、
   `bash -n` 通过)。#608 说的「fresh install 里也有」指的是新建 **SubOS**,
   而 payload 在 `data/xpkgs` 是全 home 共享的 —— 建 subos 从不重新重定位它。
   **索引仓不需要改动。**
3. **D7「注册的 shell 脚本必须能 parse」不成立** —— 发布前拿真机 49 个注册脚本量了一遍:
   3 个被拒,**2 个是假阳性**。`pip` / `pip3` 是刻意写的 sh/python polyglot,第 2 行就
   `exec` 走了,而 `sh -n` 解析整个文件。发出去会让**每台机器上的 `xlings install python` 失败**。
   已撤回。
4. **D6 第一版把 ldd 的 flag 一起传给了 loader** —— `ldd -r f` 变成 `ld.so -r f`,
   loader 把 `-r` 当成要追踪的程序。同一个工具因为一个 flag 给出两种答案,
   比它替换掉的那个统一的错误答案更难发现。已按 glibc 自己的做法翻译成
   `LD_WARN`/`LD_BIND_NOW`/`LD_DEBUG`/`LD_VERBOSE`。
5. **D2 第一版把「文件不存在」一律当成「没观测到」** —— 于是全新的 home 根本不写表,
   正是本 PR 要修的 bug 的镜像。被 `project_shim_mirror_test` 抓到。正确的是三态。
6. **`sync_one` 对「刚写过的那个 scope」硬编码 `observed=true`** —— 无项目 / `-g` 时那个
   scope **就是**全局 subos,于是最常见的那条路径仍然会从读不出的 workspace 重建。自我 review 时发现。
7. **「`self init` 在 install 和 update 时都会跑」** —— **机制写错了**,而且写进了 AGENTS.md。
   xlings 的 recipe 白纸黑字说 upgrade 不走 `self init`。结论(升级会修好)仍然成立,
   但原因是**安装路径**带的 `sync_shim_tables`,不是 init。实测:
   `use`/`install` 修复,`self init` 修复,只读命令不变。
8. **`outcomes.size() - failed` 算错了 success** —— 记录里也放着「本来就装好的」那些,
   于是 `install A B`(A 已装)会报两个安装,而它替换掉的计数器报一个。
   `N package(s) installed` 是 mcpp 会渲染的 wire 值,必须保持原意。

## 5. 实现期间新发现的缺陷:两条 agent 调用删光一个 home 的全部 SubOS(#611)

不是读代码读出来的,是量 D5 影响面量出来的。12 个声明 `required` 的能力里
**6 个对 `{}` 退出 0**;其中一对是数据丢失:

```console
$ xlings interface create_subos --args '{}'   # {"exitCode":0}
$ xlings interface remove_subos --args '{}'   # {"exitCode":0}
subos before: current default keepme
subos after:  (空的 —— 连 subos 根目录都没了)
```

R7 闭包检查把机制量得更具体:`create_subos {"name":""}` 是把 subos 的**骨架**
铺进了 `<home>/subos/` 本身:

```
<home>/subos/
  bin/ lib/ usr/ generations/ .xlings.json   ← 骨架
  default/ current keep/                      ← 真的 subos
```

所以这一对是:**先把根目录污染成一个 subos,再把根目录删掉**。
CLI 走不到(解析器要求参数)——有人在前面看着的那条路恰好是安全的。
同类的 `remove_package` / `remove_repo` / `use_version` 自己会拒绝空目标,不受影响。

## 6. 自己的验证脚本也会说谎

生态验证脚本一次跑出**一个假失败 + 一个假通过**,两条都只有读输出才会发现:

| 断言 | 错在哪 |
|---|---|
| `grep -oE '[0-9]+ missing'` | 匹配到了 broken payload 路径里的 `aria2-next/2.5.5 missing`,报了一个不存在的 shim-table 失败 |
| `grep -qiE "mcpp"` | 匹配到了 `mcpp: command not found`,给一个**不存在**的工具报了通过 |

而且 mcpp 那条本来就问错了对象:新建的 subos 里什么都没装,该去 `default` 里问。
修正后 15/15 全过,`mcpp 2026.9.18.3` 是真的版本号。
