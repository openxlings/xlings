## 3. `info` 的 2.37 秒:不是算得慢,是算了不该算的

全部为用户态 CPU,且**与包无关** —— gcc(576 行配方)与 proot(60 行)同为 2.38s,而 `search`(同样加载索引)只要 0.06s。

gdb 采样定位到 `assemble_inventory → build_owner_coordinates → shallow_owner_candidates_for`:它对**每个** pair 做一次图遍历,问「你能不能到达匹配 filter 的东西」。这个 home 有 1312 包 / 1808 条版本记录,于是整张图被走了 1808 遍。

关键观察:**那个遍历是无向的**(同时走 `incoming` 与 `bindings`)。所以「P 能到达匹配的 Q」与「Q 能到达 P」是同一句话,答案是从匹配节点**向外走一遍**,而非每个节点向内走一遍。

| | 2026.8.22.3 | 零分配后 | 反转后 |
|---|---|---|---|
| `info gcc` | 2.37 s | 1.26 s | **0.14 s** |
| `list gcc` | 0.83 s | 0.46 s | **0.11 s** |

**不做缓存**,而且理由比"没必要"更强:目标 0.5s 已被反转以 0.14s 达成,`info` 现在比"仅加载索引"只多 0.08s。缓存会把一个**不该存在的计算**存起来,并引入陈旧数据风险 —— 而这个代码库反复被"报告成功却什么都没做"咬过。

### 反转错了两次,都是测试抓的

**其一,漏了 `bindingGroup` 的提前返回分支。** 带组的 pair 原本只看组根、完全不走图;我把它们当成图节点,可达集变得**比原来更宽**。`ValidModernGroupCanFallBackToItsRoot` 失败。

**其二,种子扫的是版本 DB 而非 `requested`。** 一个在 workspace 的 `installed[]` 里、版本 DB 却无记录的版本(inactive 且 payload 已失)永远进不了集合,`list <target> --all` 因此少一行。`E2E-70` 失败。

第二个尤其值得记:**它落在"变快"与"少做事"的分界线上。** 我做了输出逐字节比对,五组全绿 —— 但比对跑在**我这台机器的 home** 上,而它恰好没有那种版本。**逐字节比对只在你比对的那些输入上成立**,它是必要条件,不是充分条件。

最终四类来源分别建模:

| 来源 | 匹配后的效果 | 代价 |
|---|---|---|
| `direct` / `payload` | 扩散到整个连通分量 | 一次 BFS |
| `provider` | 只匹配该 pair 自己 | 无 |
| `bindingGroup` | 逐 pair 直查 | 无 |
| 在 `requested` 而 DB 无记录 | 逐 pair 直查兜底 | 无 |

## 4. i18n:翻了脚手架,漏了内容

2026.8.22.3 翻译的是 `ui/banner.cpp` 里**手写的顶层表**;所有子命令的描述在 `cli/spec.cpp`,一条未接。结果是中文标题包着英文内容 —— **比全英文更糟,它让人以为翻译坏了**。

103 条描述接入,覆盖命令、选项、位置参数各层。加上面板表头(8)与交互提示语,zh 条目共 **155** 条。

**英文原文即是键。** 方案原打算给每条配 `cmd.*.desc` 形式的 ID,那要改 `spec.cpp` + `en.cppm` 共 206 行。改用原文作键后:`spec.cpp` 一个字未改,`en.cppm` 无需新增(`tr()` 找不到就返回键,而键就是英文),只有 `zh.cppm` 增量补充 —— 这也让翻译能逐条推进而非全有全无。

两个方案假设被实测推翻:cli-spec parity 检查比对的是**旗标**而非描述(271 个拼写),所以无需合并两份;而只有 `spec.cpp` 会到达用户,`cli.cpp` 的 49 处 `.description()` 喂给的是从不显示的 usage。

## 5. 选择器:形态归主题所有

配色是硬缺陷:六处彩色元素里有六处用 `theme::border()` = `#334155`,对 `#0D1117` 背景约 **1.6:1**,而正文可读下限是 4.5:1。

形态问题是它与产品其余部分不是一套语言:六行框,而 `xlings subos`/`xlings list`/每条诊断都是左对齐、`◆` 标题、`▸` 当前项。

三种形态,内置三主题各用一个 —— 不是为了给选项:**为单色终端做的配色与为投影仪做的配色,对"要不要装饰"的答案本就不同**。

| 主题 | 形态 | 理由 |
|---|---|---|
| `default` | inline | 与其余输出同一套语言 |
| `mono` | plain | 无图标无强调色 —— 那正是单色终端用不上的东西 |
| `high-contrast` | framed | `accent` 画的重边框;投影仪上边界就是可读性 |

**`framed` 的边框用 `accent` 而非 `border`。** 「太暗」的根因不是"有框",是拿 `#334155` 去画需要读的东西。`border` 仍只用于面板细分隔线。

`selector` 字段与颜色槽同一套语义:不写继承,写错**报告**而非静默回退。`tests/scripts/test_selector_contrast.py` 按 WCAG 计算比值并入 CI;把 `border` 放回去它会失败。

## 6. 六个既有缺陷

| | 症状 |
|---|---|
| `xlings subos use -h` | 标题与用法行显示 `xlings use` —— 丢了 `subos` 一层,而 `xlings use` 是真实存在、语义完全不同的命令。**照抄那行会跑错命令** |
| `info` vs `install` | 同一个名字,一个说"索引里没有",一个说"有五个"。`info` 根本不做模糊匹配 |
| macOS 构建 | `formatter<const char*, wchar_t>` —— 16 处既有代码,被我新加的**一行 import** 推过 clang 临界点 |
| §3.3 清单 | 三项被误列为缺口(`why`/`update` 的无参已有含义;`--force` 不该变成提问) |
| prompt kind | 8 个调用点有 2 个靠默认值而非声明拿到正确的层 |
| `smoke.sh` 的 `fail` | (2026.8.22.3 已修)调用了从不存在的函数 |

## 7. 这一轮自己制造又自己抓到的两个

给 `info` 加模糊匹配时:

**把两种失败当成了一种。** `resolve_target` 会报「跨命名空间歧义」(索引**确实有**该名字)与「没找到」。我在两者之后都套模糊搜索,于是**用猜测替换了一条精确诊断**。E2E-31 断言的正是那条措辞。

**生成了一条照抄会失败的命令。** 无版本的匹配项产出 `xlings info xim:config-other-platform@` —— 末尾裸 `@`。E2E-76 抓到。

第二条尤其说明问题:它发生在我**刚修完** `subos use -h` 同类缺陷之后。知道规则不能避免它,**检查输出才能**。
