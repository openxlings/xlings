# 2026.8.11.1 —— 「这个包装了吗」只剩一个回答方

> 配套发布:`xim-pkgindex#601`(graphics 0.1.4)。**必须成对**,理由见 §4。
> 分诊与证据:`.agents/docs/2026-08-11-five-issues-triage-and-plan.md`

## 1. 一句话

一个问题有四个回答方、四份数据源、零对账,于是一台真实机器上四条通道**一致地报告健康**,
而它的图形栈没有接到任何地方。这一版把那个问题收回到**一个谓词**,并让**失败自己留下记录**,
从而变得可重试。

## 2. 改了什么

### 2.1 `installation_state` —— 唯一的回答方(架构)

以前:

| 谁在问 | 读哪 |
|---|---|
| `install`(要不要跑 hook) | store 目录存在且非空 |
| `info` / inventory | xvm 记录 + 打了戳的载荷浅扫 |
| `remove`(不带版本) | 当前 active binding |
| 加载器 | `<subos>/lib` 盘上的符号链接 |

现在:`xim/install_state.cppm` 一个谓词,三态 —— `Absent` / `Installed` / `Incomplete`,
所有调用方向它提问。

### 2.2 失败自己留下记录(稳定性)

install/config hook 失败时,在**载荷上**写下失败标记。这一条单独解开 #541 ① 的闭环:
以前 hook 失败留下一个非空目录,`install` 读的那份源说「已装」,hook 永远不再跑 ——
**修复命令自己的前置条件,被它要修的残骸满足了。**

**推断行不通,试过**:「没有戳」曾是显而易见的判据,而它是错的 —— 真实 home 上没有戳的载荷
是**戳出现之前**装的老包(`linux-headers` 带着完整的 `include/` 树、二十五个被取代的
`xlings` 版本),不是失败。把它们当成 incomplete 会永远重装,正是本仓库已有事后分析的
那种不收敛。

### 2.3 戳记录它注册了什么

`.xpkg-install.json` 新增 `registered`:这次安装产生了多少个 xvm 节点。
它让「安装完成了」从一句断言变成一件可核对的事 —— 在此之前,**一次跑到终点的安装和
一次真的干了活的安装,输出完全相同**。

**「没有」不是「零」。** 早于该字段的戳描述的是一次我们没有观测过的运行,它**不产出任何判定**,
所以没有任何现存 home 会因为升级而开始重装自己。

### 2.4 `doctor` 报出两件事,修一件

| 发现 | 级别 | `--fix` |
|---|---|---|
| `incomplete install` —— 载荷的戳记录着上次安装失败 | **Error**(计入退出码) | 重跑安装 |
| `unverified install` —— 戳早于 `registered` 字段,且版本库完全没有引用它 | Notice(不计数) | 不自动修,给出命令 |

第二条是给**已装机器**的通道:那 26 个(实测)几乎正好就是图形栈。
**不自动修**,因为对这些载荷我们分不清「按设计就不注册」和「注册失败了」——
那次运行没被观测过,而人加一条命令就能定论,猜不能。

实测:`self doctor` 在 340 个载荷的 home 上 **0.74s**,与改动前持平。

### 2.5 `XLINGS_SUBOS_LIB`(E2a 契约)

由 **subos 自己**声明的 `<subos>/lib`。两个消费方读它:binutils 载荷里的 `ld` 包装器
(`-rpath-link`,以及未退出时的 `-rpath`),和 `mcpp pack`(知道该剥掉哪个目录,#540)。

进入 subos 的**两条路都声明**(spawn 与 `--sandbox`),shell profile 也重新推导一份
(profile version 10 → 11),否则一个只在其中一条路上成立的契约,消费方没法依赖。

### 2.6 `remove` 的三条提示带上版本(#541 ②)

`xlings remove <name>` 走的是 **active** binding,而在这些错误被抛出的每一种情形里,
active 都**不是**要清的那个版本 —— 于是官方出路报「未安装」,只剩工具自己警告的 `--force`。

### 2.7 `matrix.sh` 不再测量自己的探针

主表曾用裸 `gcc ... -ldl` 编探针,产物是 DT_RUNPATH,**于是每个 subos 格子测的都是
一个 DT_RUNPATH 消费者看到什么**。那个读数被当成驱动缺陷立了 #534,追了几个小时。

现在主表在**两种消费者标签下各跑一遍**(两者都是真实人群:已安装程序自 libxpkg 0.0.57
起是 DT_RPATH,subos 里构建的产物仍是 DT_RUNPATH),并且**断言探针真的带着表头声称的
那个标签** —— 否则这一行不可证伪,一次 specs 变更就能让它在 DT_RUNPATH 的数字上印一个
自信的 DT_RPATH 表头。

## 3. 索引侧(`xim-pkgindex#601`,graphics 0.1.4)

`native` 在面板上是**通过**。`host_vendor_behind` 对三种互不相干的情形都返回 `nil`,
调用方把每个 `nil` 都变成了那个通过。实测:**六个 vendor 全部记成 `native`**。

两条独立的混淆:

* `os.iorun` 失败返回 `""`,「readelf 没跑成」成了「这是我们自己的,不用查」。
  **兄弟函数 `vendor_closure_gaps` 恰好防住了同一件事**,守卫就在隔壁。
* 0.1.2 起 GLX/GLES vendor 是**指向宿主驱动的裸符号链接**。宿主库没有绝对 DT_NEEDED
  (它用 soname 命名兄弟),于是「没有绝对项」被读成「我们自己构建的」。
  **判定对最该检查的那几个 vendor 是反的。**

## 4. 为什么必须成对发布

`.wiring` 的 state 由索引侧的 recipe 在装机时**写**,xlings 只**读**。
单独发 xlings,面板能渲染新状态但没有人写它;单独发索引,写了新状态而旧客户端读不懂。

发布后的验收判据(必须在真实 home 上跑):

```sh
xlings update && xlings install graphics@0.1.4 -y && xlings use graphics 0.1.4
grep -E "state=(needs-transitive-consumer|unverified)" \
  <libglvnd载荷>/lib/glx-vendor/.wiring        # 必须命中,不得再是六行 native
```

## 4.5 合入前的自审(逐角度,含它自己找到的缺陷)

**自审找到本轮改动自己的三个缺陷,都已修**,见 commit `52b4d24`:

1. **架构 —— planner 是第五个读者。** 谓词只接在执行期,`resolve()` 仍然只看目录。
   实测同一次运行里既打印「nothing to do / already installed」又重跑了 hook。
   两处现在读同一个谓词。
2. **兼容性 —— 重新打戳丢了 foreign 守卫。** 写 `registered` 也会重写 `os`,
   等于把别的平台的载荷认领为本平台。原注释说得很清楚「无条件打戳比不打更坏」,
   第一版丢了它,因为**要加的字段感觉和会被破坏的字段无关**。
3. **安全 —— doctor 的 remedy 把来自文件系统的 namespace 交给了 shell。**
   这条发现由**扫描 store** 构建,namespace 是个目录**名**;target 和 version 检查了,
   偏偏那一段没有。现在整条 remedy 都检查。

| 角度 | 结论 | 依据 |
|---|---|---|
| **架构** | 一个谓词,四个调用方;`PackageMatch::installed` 降级为**输入**而非并列答案 | 全仓 grep:再无第二个「是否已安装」的回答方 |
| **稳定性** | 失败→标记→重试→成功清除;`remove` 连载荷带标记一起删,不会永久唠叨 | 隔离 home 实测全链路 |
| **兼容性** | 老 home **零行为变化**:无标记、无 `registered` 字段 ⇒ 不产出判定 | 真实 home:340 载荷,`install`/`info` 判定与改动前一致 |
| **无感升级** | 老 home 的问题走 `doctor` Notice + 一条命令,不自动改 | 实测 26 条,不计入退出码 |
| **一致性** | planner/installer/inventory/info/doctor 同源 | 「already installed」出现 0 次 |
| **用户体验** | `incomplete` 有原因、有修复命令;`remove` 提示带版本 | —— |
| **性能** | `self doctor` **0.74s**(340 载荷),与改动前持平 | 计时实测 |
| **跨平台** | 路径经 `platform::dir_entries` / `expand_path` / 反斜杠归一;pwsh profile 同步 | CI windows/macos 矩阵 |
| **优雅** | 新增一个模块、删除零个并列判据;`registered` 复用既有戳文件,不新增产物 | `payload_has_content` 本就按名忽略戳 |

**没有改的一件事,故意的**:`remove` 不带版本时仍然打 active。本轮只修了**提示**
(让它说出要带版本)。改它的目标解析是更大的语义变更,方案写在分诊文档 §4 P0-6,
不在一个已经很大的 PR 里顺手做。

## 5. 已知边界

* **一台机器,一种硬件**(NVIDIA / X11 / x86_64)。
* **E1a 迁移仍未做**:已装可执行文件 17 RPATH / 24 RUNPATH,那 24 个拿不到 GPU,
  面板不会为它们说话。
* **#532 构建侧(E2b)未落地**。在修好的环境上逐字复现,A 与 B 都成立:
  `gcc -lz` **链得上、跑不起来**(产物 RUNPATH 只有 glibc+gcc 两个载荷,而 `libz.so.1`
  就在 `<subos>/lib`);`gcc -lGL` 报 `libGLdispatch.so.0 / libGLX.so.0 not found`
  —— 两个库在同一个目录里。E2a 契约已就位,`ld` 包装器是下一步;`-rpath-link`
  那一半对 mcpp 无害,可以先走。
* **一条撤回**:分诊文档 §1.2.1 原先写「连 hello world 都链接不了」,那是**我把环境
  搞坏了** —— `$XLINGS_HOME/bin/xlings` 被换成 `local:xlings@0.4.51`,而它早于
  `${XLINGS_DYNAMIC_SUBOS_DIR}` 展开,标记落到 shell 手里成了空的 `--sysroot=`。
  换回 2026.8.11.1 后同一条命令 BUILD+RUN OK。
* **产品侧待办(第三次踩到)**:`self install` / `quick_install` **不认 `XLINGS_HOME`,
  只认 `HOME`**。仓库里其余隔离都靠 `XLINGS_HOME`,这两条不是,于是「设了 XLINGS_HOME
  就以为安全」的验证步骤会直接写用户真实的 home。应当二选一:尊重 `XLINGS_HOME`,
  或在只设了它时拒绝并说明。
* **#541 ③ 已证伪**(xlings 侧),真实形态在索引侧;`<subos>/lib` 里无人管理的条目
  目前没有任何检查能发现,列为后续。
* **`.wiring` 的 provenance(P1-1)未做。** 记录由 `graphics` 写、内容却是关于**别的包**的,
  那些包升级时没有任何机制让它失效(§2.3:记录比它描述的载荷早 57 秒写下)。
  本轮只修了写入侧的两个错判,**没有加 stale 检测** —— 因为它需要读写两侧同时改,
  而给一个没人写的字段先加读取方,正是本仓库「offered, never consumed」那条老毛病。
  留给下一轮成对做。
