# 2026.8.11.2 —— 「现在跑的到底是哪一个」

> 配套发布:`xim-pkgindex`(binutils 2.42.1 + graphics `payload=`)。
> 方案:`.agents/docs/2026-08-11-post-release-optimization-plan.md`
> (其中**两条前提被本轮实测推翻**,已在原文就地更正)

## 1. 一句话

上一版把**「这个包装了吗」**收回到一个谓词。这一版收它的孪生问题:
**「现在跑的到底是哪一个」** —— 入口二进制、隔离目标、未展开的标记、派生记录,
四件事都是同一个形状:**一个声明和它描述的现实可以长期不一致,而且不一致时的输出
与一致时完全相同。**

## 2. 先说两条被推翻的前提

方案是上一轮写的,落地第一步是**去量它**。两条没活下来,记在这里而不是悄悄改掉。

### 2.1 「入口是拷贝漂移」→ **不是,是按设计写的**

方案说「`bin/xlings` 是另一份拷贝,没有任何东西对账」。查代码:

| 谁写入口 | 在哪 |
|---|---|
| `xlings use xlings <v>` | `xvm/commands.cppm:618`(self-replace) |
| `xlings install`(装的就是 xlings 且成为 active) | `xim/installer.cppm:2060`,**同一动作的第二份实现** |

而且这是**必须**的:`main.cpp` 的 multicall 短路不查 workspace,所以「切了 xlings 版本」
只有落到文件上才成立。所以事故链是 **`use local:xlings@0.4.51` ⇒ self-replace 写入
6 月的载荷 ⇒ 全家 shim 经它派发**,而不是什么神秘的拷贝。

**缺的从来不是写入者**,是:两个写入者、都只 `log::debug`、都不比较版本,事后没有对账。
实测该 home 至今 **`active = local:0.4.51`,文件是 2026.8.11.1** —— 我上次只修了文件,
没修绑定,留下一个活的分叉。

### 2.2 「`self install` 只认 `HOME`」→ **错的,它认 `XLINGS_HOME`**

实测(隔离 `HOME` + 隔离 `XLINGS_HOME`,已发布的 2026.8.11.1):
`XLINGS_HOME=<iso> <rel>/bin/xlings self install` ⇒ **装进 `<iso>`**。
`detect_existing_home()` 第一句就是读 `XLINGS_HOME` 并视为权威。

**我在 memory 里记了三次的那条,从来没被验证过。** 真正的坑窄得多,而且恰好就是
每次踩的那一种:`XLINGS_HOME` 指向**源目录自己**时(解包 release、`cd` 进去、
把 `XLINGS_HOME` 指向它做隔离验证),`sameDir` 分支**静默改投 `$HOME/.xlings`**。

## 3. 改了什么

### 3.1 `entry_binary.cppm` —— 一个读者,一个写入者(架构)

`<home>/bin/xlings` 是**每一个 shim 的派发点**(`subos/<s>/bin/<tool>` 是指向它的链接),
所以它的版本决定全家工具的行为。现在:

* **一个写入者**:`replace_with()`,两处调用点都收敛到它
* **写的时候说出方向**:升级 `info`,**降级 `warn`** 并说明后果。
  不拒绝 —— 钉住旧客户端是合法操作(二分回归、复现用户报告),
  要治的是「悄悄发生」,不是「发生」。
* **一个读者**:`version_of()`,**跑那个二进制**问它。
  不读记录 —— 这个检查存在的理由就是记录和文件不一致,拿记录去校验记录看不见它。
  60ms,实测。

### 3.2 `self doctor`:长期分叉(稳定性)

两种形态,分开报,因为下一步动作不同:

| 形态 | 说明 |
|---|---|
| 绑定说 A,文件报 B | **可证的分叉**。写入者只有 `use`/`install`,所以到达此状态只能是手工拷贝或替换失败 |
| 文件落后于本 home 已装的某个版本 | **方向性判据**。「不等就报」会对每一个有意钉住的入口误报 |

修复命令**朝更新的一侧**对齐 —— 显而易见的写法(「让文件符合绑定」)在产生本检查的
那个案例里恰好**会重建事故**:绑定是 6 月的 `local:`,文件是当前版。

实测代价:同一台机器同一个 home,**改动前 1.24s,改动后 1.23s**。

### 3.3 命名空间优先级:`local` 排最后(用户体验)

二义即拒绝,是**「没有规则」时**的正确做法。`local` 不是对等的命名空间 ——
它是旁路装载的那个,dev 脚本丢进去的 recipe 会永远留着 —— 而拒绝的代价实测过:
`self update` 因 `local:xlings` 与 `xim:xlings` 打平而拒绝,**于是没人升级入口**。

规则刻意做到最小:降 `local`,**不发明其余命名空间之间的顺序**(那才是确定性契约
禁止的静默选择),显式限定的目标不受影响,**并且把输掉的那个说出来**。

announce 放在 catalog 里去重发出,因为 `resolve_target` 有十六个调用方,
逐个加一行必然漏一个,而漏掉的那个就是一次静默选择。

### 3.4 `${XLINGS_*}` 不再变成空值(稳定性)

判据是**「这个引用会不会展开成空」**,不是「它是不是我们的标记」。名单两头都错:

* 它**装不下**造成事故的那个名字 —— 那个名字是在这个客户端发布**之后**被发明的
* 它会**误杀** `${XLINGS_SUBOS_LIB}` —— recipe 故意交给环境,`ld` 包装器正是这么用的

一次 `getenv`,不需要字典。

同时,**shim 自己声明 `XLINGS_SUBOS_LIB`**。原来三层声明它(profile / spawn /
`--sandbox`),三层覆盖的都是**进入 subos**;shim 是程序启动的第四条路 ——
从没 source 过 profile 的 shell 里跑 `gcc`,或构建系统清过环境。
读这个变量的 `ld` 包装器在那条路上会**什么都不做,而这与它工作时无法区分**。

### 3.5 `self install`:冲突拒绝 + 方向感知的确认(兼容性)

* `XLINGS_HOME` 与将要写入的目标不一致 ⇒ **拒绝并列出两条路径**。
  只在冲突时,所以不设 `XLINGS_HOME` 的普通安装零变化。
* 覆盖确认现在**说出两个版本和方向**,降级时默认 **No**。
  旧的默认是**反着的**:重装同版本谨慎地问,回退六周直接默认 Yes。

### 3.6 `remove <name>` 多版本时列出并退出 2(一致性)

`use <target>` 早就立了规矩:**「有没有人在键盘前不可检测,这条命令有没有唯一正确
结果可以检测」**。差别在于 `use` 不带版本是**查询**(答完了,退 0),
而 `remove` 是**动作** —— 什么都没删还退 0,正是本仓库反复付账的那个形状。
所以列出 + 退 2(`remove` 已有的「拒绝,什么都没做」码)。
单版本不变,`--force` 豁免(recipe hook 走这条路,它已经决定了要替换什么)。

### 3.7 `.wiring` provenance(跨仓库,读写成对)

记录由 `graphics` 写,每一行说的都是**别的包**。实测物证:记录写于 `01:37:17`,
它描述的 nvidia 载荷写于 `01:38:14` —— **判决比它的对象早 57 秒**。

写入侧记 `payload=<载荷目录>`(放行末,因为路径可能有空格);
读取侧**只做本地对照**:`glx-vendor/<soname>` 的符号链接是否仍落在该目录之下。

为什么不是「盘上版本与记录不符」:**读取方答不出来**。`subos info` 按契约是
即时本地查询、不解析索引,所以那种判据落地当天才会发现做不了。

**没有 `payload=` ⇒ 不产出判定。** 所有既有 home 的记录都没有这个字段,
把它们判成 stale 就是拿一个没人写过的字段去否定整个图形栈 —— 和把「没有 `registered`」
当成「零」是同一个错误。

### 3.8 binutils `ld` 包装器(#532 第一步)

实测复现,`ld` 自己的报错就写着修法:

```
ld: warning: libGLdispatch.so.0, needed by <subos>/lib/libGL.so, not found
    (try using -rpath or -rpath-link)
ld: <subos>/lib/libGL.so: undefined reference to `__glDispatchInit'
```

加 `-rpath-link <subos>/lib` 之后**链接通过**(也已实测)。

放在 binutils 载荷里,注册到 `xlings-wrappers/`,`bin/` 一个字节不动 ——
不与装机期的 ELF 检查(elfpatch auto、closure_check rule E)打架,
也不需要给真的 `ld` 起一个别人得知道的新名字。

包装器里**没有 home 路径、没有 subos 路径、没有版本**:它读 `XLINGS_SUBOS_LIB`。
所以每个 home 里都是同样的字节,`xlings use binutils <ver>` 不需要重写它。
值是**判断**而不是插值 —— `-rpath-link ""` 不是「没有这个选项」,而是「当前目录」,
这正是 `--sysroot=` 那次的同一种空值/缺失混淆。

## 5. 自审抓到我自己的缺陷

**`self install` 的守卫读 `getenv("XLINGS_HOME")`** —— 而 `main.cpp` 每次运行都会把
它导出成自己解析出的 home。于是守卫读到的是**xlings 自己的答案**,拒绝了一个
明明传了 `env -u XLINGS_HOME` 的调用方。

**「一个问题多个回答方」,而第二个回答方是我。**

抓到它的是 `shim_link_test.sh` —— 一个**从来没在任何地方跑过**的 e2e,
在这一轮被清理孤儿时第一次运行。这条比修复本身更值得记。

修法:在 `main.cpp` 导出**之前**显式捕获(`Config::ambient_home_env`)。
不用静态初始化顺序 —— 那个论证是对的但读者无法验证,而「输入的含义会悄悄变」
正是本轮在治的病。

## 6. 已知边界

* **一台机器,一种硬件**(NVIDIA / X11 / x86_64)。
* **#532 的运行期那一半(`-rpath`)未做。** 本轮只做链接期的 `-rpath-link`:
  它**不写进产物**,所以对 mcpp 无害、不需要等 #540 谈完退出形态。
  `gcc -lz && ./a.out` 仍然跑不起来,这是明确的下一步。
* **`quick_install` 未验证**。本轮只量了 `self install`;既然关于它的记录已经
  被推翻一条,关于 `quick_install` 的那条也应当**先量再信**。
* **3.7 `<subos>/lib` 无人管理的条目**未做 —— 按方案,它要等 provenance 落地后
  一起做,才有正证据可用。
