# 2026.8.11.2 —— 「现在跑的到底是哪一个」

> 配套发布:`xim-pkgindex`(binutils 2.42.1 + graphics `payload=`)。
> 方案:`.agents/docs/2026-08-11-post-release-optimization-plan.md`
> (其中**两条前提被本轮实测推翻**,已在原文就地更正)

## 1. 一句话

上一版把**「这个包装了吗」**收回到一个谓词。这一版收它的孪生问题:
**「现在跑的到底是哪一个」** —— 入口二进制、隔离目标、未展开的标记、派生记录,
四件事都是同一个形状:**一个声明和它描述的现实可以长期不一致,而且不一致时的输出
与一致时完全相同。**

## 2. 先说两条被推翻的前提

方案是上一轮写的,落地第一步是**去量它**。两条没活下来,记在这里而不是悄悄改掉。

### 2.1 「入口是拷贝漂移」→ **不是,是按设计写的**

方案说「`bin/xlings` 是另一份拷贝,没有任何东西对账」。查代码:

| 谁写入口 | 在哪 |
|---|---|
| `xlings use xlings <v>` | `xvm/commands.cppm:618`(self-replace) |
| `xlings install`(装的就是 xlings 且成为 active) | `xim/installer.cppm:2060`,**同一动作的第二份实现** |

而且这是**必须**的:`main.cpp` 的 multicall 短路不查 workspace,所以「切了 xlings 版本」
只有落到文件上才成立。所以事故链是 **`use local:xlings@0.4.51` ⇒ self-replace 写入
6 月的载荷 ⇒ 全家 shim 经它派发**,而不是什么神秘的拷贝。

**缺的从来不是写入者**,是:两个写入者、都只 `log::debug`、都不比较版本,事后没有对账。
实测该 home 至今 **`active = local:0.4.51`,文件是 2026.8.11.1** —— 我上次只修了文件,
没修绑定,留下一个活的分叉。

### 2.2 「`self install` 只认 `HOME`」→ **错的,它认 `XLINGS_HOME`**

实测(隔离 `HOME` + 隔离 `XLINGS_HOME`,已发布的 2026.8.11.1):
`XLINGS_HOME=<iso> <rel>/bin/xlings self install` ⇒ **装进 `<iso>`**。
`detect_existing_home()` 第一句就是读 `XLINGS_HOME` 并视为权威。

**但那条记录在写下的时候是对的。** `git log -L` 查到 `0c362cf`(2026-08-03,
随 2026.8.3.1 发布)之前的代码是:

```cpp
if (fs::exists(p / "bin") && fs::exists(p / "subos"))
    return fs::weakly_canonical(p);
```

—— **只有当 `XLINGS_HOME` 已经是一个成型的 home 时才认它**。一个空的隔离目录
不满足这个条件,于是掉进 PATH 发现,找到真实 home。2026-07-30 和 2026-08-01
两次观测都是这个形态,记录准确;**是产品改了而记录没跟**。

教训因此换了一条,而且更重要:**一条关于产品行为的记录会随产品过期,
但它读起来永远像事实。** 引用一条记录去做设计判据之前,要么它带着「在哪个版本上量的」,
要么就重新量一次。本轮的 §3.2 就是照着一条过期记录写的。

真正的坑窄得多,而且恰好就是每次踩的那一种:`XLINGS_HOME` 指向**源目录自己**时
(解包 release、`cd` 进去、把 `XLINGS_HOME` 指向它做隔离验证),
`sameDir` 分支**静默改投 `$HOME/.xlings`**。

## 3. 改了什么

### 3.1 `entry_binary.cppm` —— 一个读者,一个写入者(架构)

`<home>/bin/xlings` 是**每一个 shim 的派发点**(`subos/<s>/bin/<tool>` 是指向它的链接),
所以它的版本决定全家工具的行为。现在:

* **一个写入者**:`replace_with()`,两处调用点都收敛到它
* **写的时候说出方向**:升级 `info`,**降级 `warn`** 并说明后果。
  不拒绝 —— 钉住旧客户端是合法操作(二分回归、复现用户报告),
  要治的是「悄悄发生」,不是「发生」。
* **一个读者**:`version_of()`,**跑那个二进制**问它。
  不读记录 —— 这个检查存在的理由就是记录和文件不一致,拿记录去校验记录看不见它。
  60ms,实测。

### 3.2 `self doctor`:长期分叉(稳定性)

两种形态,分开报,因为下一步动作不同:

| 形态 | 说明 |
|---|---|
| 绑定说 A,文件报 B | **可证的分叉**。写入者只有 `use`/`install`,所以到达此状态只能是手工拷贝或替换失败 |
| 文件落后于本 home 已装的某个版本 | **方向性判据**。「不等就报」会对每一个有意钉住的入口误报 |

修复命令**朝更新的一侧**对齐 —— 显而易见的写法(「让文件符合绑定」)在产生本检查的
那个案例里恰好**会重建事故**:绑定是 6 月的 `local:`,文件是当前版。

实测代价:同一台机器同一个 home,**改动前 1.24s,改动后 1.23s**。

### 3.3 命名空间优先级:`local` 排最后(用户体验)

二义即拒绝,是**「没有规则」时**的正确做法。`local` 不是对等的命名空间 ——
它是旁路装载的那个,dev 脚本丢进去的 recipe 会永远留着 —— 而拒绝的代价实测过:
`self update` 因 `local:xlings` 与 `xim:xlings` 打平而拒绝,**于是没人升级入口**。

规则刻意做到最小:降 `local`,**不发明其余命名空间之间的顺序**(那才是确定性契约
禁止的静默选择),显式限定的目标不受影响,**并且把输掉的那个说出来**。

announce 放在 catalog 里去重发出,因为 `resolve_target` 有十六个调用方,
逐个加一行必然漏一个,而漏掉的那个就是一次静默选择。

### 3.4 `${XLINGS_*}` 不再变成空值(稳定性)

判据是**「这个引用会不会展开成空」**,不是「它是不是我们的标记」。名单两头都错:

* 它**装不下**造成事故的那个名字 —— 那个名字是在这个客户端发布**之后**被发明的
* 它会**误杀** `${XLINGS_SUBOS_LIB}` —— recipe 故意交给环境,`ld` 包装器正是这么用的

一次 `getenv`,不需要字典。

同时,**shim 自己声明 `XLINGS_SUBOS_LIB`**。原来三层声明它(profile / spawn /
`--sandbox`),三层覆盖的都是**进入 subos**;shim 是程序启动的第四条路 ——
从没 source 过 profile 的 shell 里跑 `gcc`,或构建系统清过环境。
读这个变量的 `ld` 包装器在那条路上会**什么都不做,而这与它工作时无法区分**。

### 3.5 `self install`:冲突拒绝 + 方向感知的确认(兼容性)

* `XLINGS_HOME` 与将要写入的目标不一致 ⇒ **拒绝并列出两条路径**。
  只在冲突时,所以不设 `XLINGS_HOME` 的普通安装零变化。
* 覆盖确认现在**说出两个版本和方向**,降级时默认 **No**。
  旧的默认是**反着的**:重装同版本谨慎地问,回退六周直接默认 Yes。

### 3.6 `remove <name>` 多版本时**说出来**,不拒绝(一致性)

**这一条我先写成了拒绝,被 E2E-13 打回来,而它是对的。**

方案的判据是「在 `remove` 抛出多版本相关错误的每一种情形里,active 都不是要清的
那个版本」—— 那是关于**错误路径**的证据,我把它推广到了正常路径。
而正常路径上,`remove <pkg>` 清 active 并把绑定重指到最高的幸存者,是一条
**有 bugfix 文档、有注册 e2e 的契约**(`docs/bugfixes/2026-04-25-…`),
「跑三遍清三个版本」是人真的会写的循环。

留下的是真正缺的那一半:**没有任何东西告诉用户这里还有别的版本、以及怎么点名它们。**
所以改成**列出所有版本 + 说明这次只清 active**。

这也正是本轮对入口二进制做的选择 —— **把分叉说出来,而不是拒绝它** ——
和自己保持一致本身就是大部分理由。`--force` 豁免(recipe hook 走这条路)。

### 3.7 `.wiring` provenance(跨仓库,读写成对)

记录由 `graphics` 写,每一行说的都是**别的包**。实测物证:记录写于 `01:37:17`,
它描述的 nvidia 载荷写于 `01:38:14` —— **判决比它的对象早 57 秒**。

写入侧记 `payload=<载荷目录>`(放行末,因为路径可能有空格);
读取侧**只做本地对照**:`glx-vendor/<soname>` 的符号链接是否仍落在该目录之下。

为什么不是「盘上版本与记录不符」:**读取方答不出来**。`subos info` 按契约是
即时本地查询、不解析索引,所以那种判据落地当天才会发现做不了。

**没有 `payload=` ⇒ 不产出判定。** 所有既有 home 的记录都没有这个字段,
把它们判成 stale 就是拿一个没人写过的字段去否定整个图形栈 —— 和把「没有 `registered`」
当成「零」是同一个错误。

### 3.8 binutils `ld` 包装器(#532 第一步)

实测复现,`ld` 自己的报错就写着修法:

```
ld: warning: libGLdispatch.so.0, needed by <subos>/lib/libGL.so, not found
    (try using -rpath or -rpath-link)
ld: <subos>/lib/libGL.so: undefined reference to `__glDispatchInit'
```

加 `-rpath-link <subos>/lib` 之后**链接通过**(也已实测)。

放在 binutils 载荷里,注册到 `xlings-wrappers/`,`bin/` 一个字节不动 ——
不与装机期的 ELF 检查(elfpatch auto、closure_check rule E)打架,
也不需要给真的 `ld` 起一个别人得知道的新名字。

包装器里**没有 home 路径、没有 subos 路径、没有版本**:它读 `XLINGS_SUBOS_LIB`。
所以每个 home 里都是同样的字节,`xlings use binutils <ver>` 不需要重写它。
值是**判断**而不是插值 —— `-rpath-link ""` 不是「没有这个选项」,而是「当前目录」,
这正是 `--sysroot=` 那次的同一种空值/缺失混淆。

### 4.1 §3.8 的实测,带对照(两个仓库各一半,所以必须成对)

**下半:包装器**。用 `-B` 强制 gcc 走它,只改环境变量:

| | rc | 产物 |
|---|---|---|
| `XLINGS_SUBOS_LIB` **已设** | 0 | **链接成功** |
| `XLINGS_SUBOS_LIB` **未设** | 1 | 无 —— 与今天一模一样 |

第二行同样重要:没有值时**整段消失**,不是变成 `-rpath-link ""`(那等于当前目录)。

**上半:谁来设这个变量**。同一台机器、同一个 home,只换派发的二进制:

```
新 build (2026.8.11.2)   XLINGS_SUBOS_LIB=/home/speak/.xlings/subos/default/lib
已发布 (2026.8.11.1)     XLINGS_SUBOS_LIB=(unset)
```

**这是对照,不是断言** —— 上一轮我曾把「换了被测二进制却没换派发者」当成对照,
这次两次运行只差派发者本身。

**最后一环也量到了。** 索引合入后在真实 home 上装 `xim:binutils@2.42.1`:

```
版本库记录     ld@2.42.1 -> …/xim-x-binutils/2.42.1/xlings-wrappers   ← 注册到包装器
包装器文件     sh -n 通过;`ld --version` 经它输出 GNU ld 2.42
```

然后同一台机器、同一条命令,只改环境变量:

| | rc | 产物 |
|---|---|---|
| `gcc t.c -lGL`(`XLINGS_SUBOS_LIB` 未设 = 今天) | 1 | 无 |
| 同上,变量已设(= 新 shim 会做的事) | **0** | **有** |
| 运行那个产物 | 127 | `libGL.so.1: cannot open shared object file` |

第三行**正是预期**:那是运行期的一半(`-rpath`),本轮明确不做。
链接期修好了,运行期没有,而且两者被分开说清楚 —— 这正是 §6 边界那条。

### 4.1.1 生态验证:`xlings subos default --sandbox --gpu --cmd …`

装好 `binutils@2.42.1` 之后,在**真实沙箱**里,零 flag:

```
SUBOS_LIB=/home/speak/.xlings/subos/default/lib
--- gcc -lGL ---     rc=0  artifact=yes      ← #532 的链接期,修好了
--- gcc -lz  ---     rc=0  artifact=yes
--- run s_z  ---     libz.so.1: cannot open shared object file
```

第三行是**预期**:运行期那一半(`-rpath`)本轮不做。

注意它**在旧入口下就已经成立** —— 因为 `--sandbox` 自己声明 `XLINGS_SUBOS_LIB`
(2026.8.11.1 的 E2a 契约)。2026.8.11.2 的 shim 导出把同一件事扩展到
**没 source 过 profile 的普通 shell**,那才是 `gcc` 最常被调用的地方。

### 4.2 §3.7 provenance,在真机上双向证伪

装 `graphics@0.1.5` 之后,`.wiring` 六行全部带上 `payload=`(状态不变 —— 栈没变):

```
vendor=libGLX_nvidia.so.0 state=ok payload=…/xim-x-nvidia-gl-host-link/0.1.2
```

然后**只动那一条符号链接**:

| | `subos info` |
|---|---|
| 原样 | `nvidia GLX  ok (the host driver behind it is reachable)` |
| 把它改指到 mesa 的载荷 | ⚠ `nvidia GLX  STALE — …(wired to …/xim-x-mesa/25.0.7.2/lib, recorded against …/xim-x-nvidia-gl-host-link/0.1.2)` |
| 改回去 | `nvidia GLX  ok` |

**两个方向都试了。** 只报「改了会 stale」而不验「没改不报」,是一条不可证伪的判据 ——
上一轮六个 `native` 就是那么来的。

### 4.3 一个遗漏,复查「谁能收到」时才发现

`payload=` 的写入方是 `graphics` 的 `config()`,而 **`config()` 只在包安装时跑**,
graphics 又没有载荷。所以不 bump 版本的话,**每一个既有 home 的记录都永远没有这个字段**,
而读取侧对没有字段的记录**按设计不产出判定** —— 于是读写成对做完了,
在所有真实机器上却是**惰的**。已补 `graphics 0.1.5`(xim-pkgindex#607)。

**教训**:「读写成对」还差一问 —— **写的那一半会不会真的跑?**

## 5. 自审抓到我自己的缺陷

**`self install` 的守卫读 `getenv("XLINGS_HOME")`** —— 而 `main.cpp` 每次运行都会把
它导出成自己解析出的 home。于是守卫读到的是**xlings 自己的答案**,拒绝了一个
明明传了 `env -u XLINGS_HOME` 的调用方。

**「一个问题多个回答方」,而第二个回答方是我。**

抓到它的是 `shim_link_test.sh` —— 一个**从来没在任何地方跑过**的 e2e,
在这一轮被清理孤儿时第一次运行。这条比修复本身更值得记。

修法:在 `main.cpp` 导出**之前**显式捕获(`Config::ambient_home_env`)。
不用静态初始化顺序 —— 那个论证是对的但读者无法验证,而「输入的含义会悄悄变」
正是本轮在治的病。

### 5.2 `remove` 的拒绝被 E2E-13 打回

我按方案写成「多版本 ⇒ 列出并退 2」。E2E-13(已注册,而且跑在 macOS/Windows
矩阵上)当场变红,**而它是对的**:见 §3.6。

值得记的是判据的来源:方案那句「active 从来不是要清的那个」是从 **#541 ② 的错误
路径**上得来的证据,我把它推广到了正常路径。**一条在 A 情形下成立的观察,
不因为听起来一般就在 B 情形下成立。**

### 5.3 命名空间优先级只在一半路径上出声

`resolve_target` 会打印降权行,`resolve_local_identity`(inventory 走这条)
**不会**。于是一个裸名的已打戳身份会被**静默选择** —— 正是这条规则绝不能变成的
东西,也正是「规则存在之前拒绝是对的」那个论证的全部理由。两条路径现在都出声。

### 5.4 doctor 拿哨兵值当版本比

绑定可能是 `latest` 这样的哨兵。原写法会把它和入口二进制的版本直接比,
于是**任何这么写绑定的 home 都会被报成漂移**。
**没有观测不是不一致** —— 两边现在用同一条「首字符是数字」的规则做资格判定。

## 5.5 升级注意:命名空间优先级救不了还没装上它的人

这一版修的「`self update` 因 `xim:` 与 `local:` 打平而拒绝」,**修在被拒绝的那一版里**。
所以一个 home 如果同时有 `local:xlings`,它的 2026.8.11.1 仍然会拒绝,
**只能显式限定一次**:

```sh
xlings install xim:xlings@latest -y && xlings use xlings latest
```

这不是绕过,正是设计里留的那扇门:**显式限定的目标永远不受优先级影响**。
装上之后 `self update` 恢复正常。

绝大多数 home 没有 `local:xlings`,不受影响。

## 6. 已知边界

* **一台机器,一种硬件**(NVIDIA / X11 / x86_64)。
* **#532 的运行期那一半(`-rpath`)未做。** 本轮只做链接期的 `-rpath-link`:
  它**不写进产物**,所以对 mcpp 无害、不需要等 #540 谈完退出形态。
  `gcc -lz && ./a.out` 仍然跑不起来,这是明确的下一步。
* **`quick_install` 未验证**。本轮只量了 `self install`;既然关于它的记录已经
  被推翻一条,关于 `quick_install` 的那条也应当**先量再信**。
* **3.7 `<subos>/lib` 无人管理的条目**未做 —— 按方案,它要等 provenance 落地后
  一起做,才有正证据可用。
