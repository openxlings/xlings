## 1. 一句话

## 2. 用户看到的

```
改前                                       改后
[error] mcpp@2026.9.17.1 is selected       [warn] mcpp@2026.9.17.1 is the version this
        here, and no such version is              project asks for, and it is not
        installed                                 installed yet
  installed  <5 个版本>, +89 more            from       ./.xlings.json -> workspace.mcpp
  install the pinned one                    installed  2026.8.21.1, 2026.8.18.3, +92 more
    xlings install mcpp@2026.9.17.1         set this project up   xlings install
  or change the pin  edit the file above
```

三点反馈,三点都对:

| | 改动 | 理由 |
|---|---|---|
| 级别 | `Error` → `Warn`,**退出码仍是 1** | 严重级说"这有多糟",退出码说"发生了什么",允许不一致。一个离能用只差一条已知命令的项目,不是工具的故障;红色加粗会把它读成故障 |
| 动作 | `xlings install`(无参) | 那才是读项目声明的命令。手输坐标是让用户重做项目文件里已经写好的事,且项目声明多个依赖时是错的 |
| 候选 | 5 个 → 2 个 | 读者是去跑动作的,不是来挑版本的;长列表把动作挤下屏幕 |

判据现在写进了 `docs/spec/diagnostics.md` §3:**xlings 知道确切出路的用 `Warn`,需要用户自己去找答案的用 `Error`。**

## 3. 写测试时发现的:同一状态有两个答案

shim 走一条诊断,`xlings use` 走另一条 —— 后者是 `[error]` 加一个要重敲的坐标。

这正是 2026.8.22.1 整轮在治的形状(「一个问题,多个回答者」),**出现在 2026.8.22.1 刚建的东西里**。`not_in_subos` 现在走同一个 project 分支,两条路径措辞一致。

## 4. 自我 review 发现的:门控问的是错的问题

友好措辞挂在 `Config::has_project_config()` 上。那回答的是"**这儿有没有项目**";而决定 `xlings install` 是不是正确建议的,是"**哪一层钉的这个版本**"。

`xlings install`(无参)只读向上找到的 `.xlings.json` 的 `workspace`。另外两层 —— 全局 subos 文件、project-subos 文件 —— 同样会钉版本、同样会渲染出 `from` 行,而这条命令**都不读**。

于是:一个全局钉住的程序,在一个因别的原因带了项目文件的目录里 ——

```
[warn] this project asks for a version of demo that is not installed yet
  from                  .../proj/.xlings/subos/_/.xlings.json
  set this project up   xlings install
```

三处都错:

1. 项目并没有要求它;
2. `from` 指的不是项目清单;
3. 给出的命令会装**别的东西**,然后**退出 0**。

第 3 条是 succeeded-having-done-nothing —— 由治 succeeded-having-done-nothing 的那个改动生产出来的。

**根因不是判断写错了,是答案被拆成了两半。** `version_source` 内部就算出了是哪一层赢,却只返回展示字符串把层丢掉;4 个调用方于是各自用代理重建后一半。现在是 `version_origin`,一次返回 `{source, fromProjectManifest}` 两半,代理在这儿已经拼不出来了。

## 5. 测试

E2E-61 新增:

- **S2b** —— 级别是 `warn`、措辞说明来自项目、动作**必须**是无参的 `xlings install`;
- **S2c** —— 全局钉住 + 项目文件同时存在,断言它**不**被算作项目的错。

S2c 在旧代理门控下**实测失败过**(第 4 节那段就是它的真实失败输出)。没有这一步,它和"代码里没有违规"无法区分。

写 S2c 时我自己先写了 `grep -qv … || fail` —— 那是恒真的空断言(只要有任意一行不匹配就成立)。同一个坑本轮已经踩过一次(`subos_scope_authority` S3),文件里现在写了注释说明为什么用 `if grep; then fail`。
