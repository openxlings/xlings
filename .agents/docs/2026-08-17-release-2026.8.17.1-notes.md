# 2026.8.17.1 —— 「没观测过的事，不许写成事实」

> 分析与方案：`.agents/docs/2026-08-17-547-and-three-merged-prs-review.md`
> （§0 是四行结论，§2.2b/§2.3b 是 review 追问推翻第一版方案后补做的测量，
> §9 是横切观察）

## 1. 一句话

这一轮修的四件事底下是同一个形状：

> **一段代码宣称了一件它没有观测过的事，而宣称和事实长得一模一样。**

| | 宣称 | 实际 |
|---|---|---|
| `installer.cpp` 写 subos 块 | 「这个 subos 跑 glibc@2.44」 | 从没看过它跑什么 |
| 同上，另一面 | 「用户没指定所以用默认」 | `install` 根本没有 `--runtime` 可指定 |
| `make_block` 的 `created_at` | 「这个 subos 生于 2026-08-05」 | 那是**回填**的时刻 |
| `remove_payload_dir` 的回滚 | 「已回滚」 | 已**删除** |
| `index_revision_`（#552） | 「读不到 revision」 | 读得到，只是多了一个 `\r`；而且它看不见 artifact 形态的索引 |

## 2. 数字

真实 home（39 个 subos）实测：

| | 数量 |
|---|---|
| 有 `subos_info` | 5 |
| **其中声明与 sysroot 矛盾** | **2**（含 issue #547 里那个 `mcpp-test`） |
| 无 `subos_info` | 32 |
| 　其中 workspace 已记录 runtime | 17 —— 旧代码会把这 17 个全部声明成 `glibc@2.44` |
| 　其中两种证据都没有 | 15 —— 旧代码只能编一个 |

`default` 与 `gfxbuild` 的 `created_at` **逐字节相同**（`2026-08-05T03:35:16Z`）：
它们不是同一秒被创建的，是同一秒被**描述**的。

## 3. #547：六个写入方，第六个在写假话

`subos_info` 块有六处写入方。五处调同一个 helper，第六处
（`installer.cpp:1375/1382`，包声明 `subos_env` 时触发）**直接写
`DEFAULT_RUNTIME` 常量**，`preserved_runtime` 一次都没被调用。

这就是「一个问题、多个回答者」最难发现的形态：**五个都对，所以
「有没有统一入口」这个问题的答案看起来是「有」。**

### 修法不是加第七个入口

第一版方案提了 `subos repair --all` + `subos use` hook + doctor 全量扫描三件事。
review 追问「没用的 subos 为什么也要修」之后重新测量，前提被推翻：

- **懒补写已经存在**（`xim install` 就在做），覆盖基本不是缺陷；
- **`subos use` hook 有洞** —— `XLINGS_ACTIVE_SUBOS` 是继承的环境变量，
  profile 直接读它不跑任何 xlings 代码，`--global` 用户一辈子只跑一次 `subos use`；
- **给 15 个无证据 subos 补块有害无益** —— 零信息量，外加一条假的出生记录。

于是方案收窄成：**让已有的六个入口说真话。**

### `runtime_for()` + `Intent`

```
enum class Intent { Create, Describe };
```

| 顺序 | 源 | 性质 | Create | Describe |
|---|---|---|---|---|
| 1 | 块里已有的良构 binding | 声明 | ✅ | ✅ |
| 2 | `--runtime` | 人的意图 | ✅ | 参数不存在 |
| 3 | workspace 的 active runtime | 记录 | ✅ | ✅ |
| 4 | **sysroot `lib*/libc.so.6` 指向的载荷** | **观测** | ✅ | ✅ |
| 5 | `DEFAULT_RUNTIME` | 常量 | ✅ 兜底 | ❌ → **不写 `runtime` 键** |

**唯一的差别就是最后一行。** `DEFAULT_RUNTIME` 的作用域因此字面上等于它自己
注释里那句 `Scope: NEW subos only`。七个站点全部改调它，`preserved_runtime`
**在同一个 commit 里删除** —— 让「还有站点没归队」变成编译错误。

第 4 源是唯一一个**观测**而非记录的来源。其余每个答案都是上一次运行写下来的，
所以两个记录可以朝同一个方向错并且彼此一致 —— 那正是真机上发生的事。

### 「未知」现在可以表达

I6 从「`runtime` 必须是良构 binding」放宽为「**存在则必须良构，缺席合法**」。

这条不变式就是 #547 的成因：旧规则下，一次无证据的 describe 只有两个选择 ——
编一个，或者产出一个 `--fix` 会永远重写的块。**它编了一个。**

于是两种状态终于可以区分：

- 块不存在 → 写于 `subos_info` 出现之前（旧格式）
- 块存在、`runtime` 键缺席 → **看过了，说不出来**（已知未知）

树内所有 `info.runtime` 的读取方本来就先判 `is_binding`，所以对新 client 这是纯放宽，
无需 schema bump。**旧 client 的 `validate_block` 是例外，见 §7。**

### provenance 不再伪造

`created_at`/`created_by`（创建）与 `described_at`/`described_by`（事后描述）
二选一，I8 接受任一对。要求 `created_*` 正是逼着每一次回填伪造一个创建日期的原因 ——
**本该抓住 provenance 缺失的检查，反而是 provenance 被发明出来的理由。**

### 两条新 finding

- `SubosRuntimeDrift`（Warning）—— 声明与 sysroot 矛盾。**只报不修**：
  哪一边是意外这里判断不了，而静默改写声明会改变这个 subos**声称自己是什么**。
- `SubosRuntimeUnknown`（Notice，不计入退出码）—— 诚实的未知不是缺陷。
  一度藏在 `--verbose` 后面，实测发现 doctor 只检查活跃 subos，每次运行至多一条，
  「会淹没真问题」的担心不成立 —— 藏起来它就是一条没人看得到的提示。

### 顺带：`new --from … --runtime X` 不再静默丢弃 X

fork 的 runtime 由 base 决定是对的（复制过来的载荷就是按那个 libc 构建的），
**但「静默」不对**。现在会说明为什么被忽略，以及怎样才能选。

## 4. #551 的三个残留

`remove_payload_dir` 的回滚分支 `remove_all(trash)` 删掉的正是它已经挪出去的文件。

**而写测试时发现，这个缺陷比它看起来更深：**「回滚到未触碰」从来就不可达。
快路径是 `remove_all`，它不是原子的 —— 在一棵有文件被占用的树上，
它会先删掉所有能删的再报错。等我们知道有东西被占用时，别的文件已经没了。

所以真正的问题不是「我们弄坏了吗」（弄坏了，那正是用户要的），而是
**「下一次 install 会不会修好它」**。残留唯一的危险是 `payload_has_content`
对它为真：包读起来像装着的，下一次 `xlings install` 会**接收残骸**而不是重建。

于是 `Partial` 结果会把目录 stamp 成 incomplete —— `install_state` 最先检查的
就是它，和一次失败的安装留下的记号完全一样。

另外两条：

- **trash 挪出版本命名空间**。7 处代码把 `xpkgs/<pkg>/*` 每个子目录当版本读，
  **逐个核对过，没有一处过滤点号**。现在放在 `data/trash/`（同一文件系统，
  `rename` 才能成功），并且 `sweep_payload_trash` 在每次卸载前清一遍 ——
  原注释承诺的 "removed on a later run" 此前不存在任何对应代码。
- **从匿名 namespace 挪进 `xim.payload` 模块**。它此前测不到，
  这正是回滚分支能反着写还合入的原因。

## 5. #550 / #552 的收尾

- **#550 把自己诊断的缺陷又造了一遍**：论点是「参数没有调用者就不是功能」，
  而它给 `collect_matches_` 新加的 `forSearch` 参数没有任何调用者。已删除。
- **#552 的 `index_revision_` 是第二个回答者**，而 `get_repo_head_hash` 早已存在
  且**认识两种索引形态** —— git 工作树，以及没有 `.git` 的 artifact 安装。
  新读取器对后者一律返回空，会让整个特性对那些 home 静默失效。已合并为一个，
  并给它补上 `packed-refs`（旧函数也缺）。
  **顺带纠正一处我照抄的说法**：#552 的注释说 packed-refs 是「新鲜 clone 的常见形态」，
  我在分析文档里重复了它 —— 实测不成立：这台机器上四个索引仓库**都**同时有
  `packed-refs` 和 loose `refs/heads/<branch>`，`git clone` 会为签出的分支写 loose ref。
  真正产生 packed-only 的是 `git gc` / `git pack-refs`。是真的 fallback，只是不是默认路径。
- **一个超出错误文案的副作用，说清楚**：`get_repo_head_hash` 同时是解析索引缓存的 key
  （`catalog.cpp:504`）。它此前在读不到 loose ref 时返回空 → 缓存被禁用 → 每次
  `install`/`search` 全量重建索引。补上 packed-refs 之后，那种仓库开始命中缓存。
  是改进，但它不在「改错误文案」这个标题下面，所以写在这里。
- **CRLF**：`packed-refs` 分支不剥 `\r` 却做精确长度比对，一旦文件带 CRLF
  就必然匹配失败 → 退回旧文案，**没有任何提示**。
- **`xlings update` 的建议改为按索引新鲜度门控**。正文承诺的「贴在它适用的
  场景上」此前没有实现：只要读得出 revision 就无条件拼上，而那对刚同步过的人
  是无效建议 —— 正是它要消除的噪音。

## 6. Windows CI 红的方式最坏

`TaskManager.PromptHandling` 用 100×10ms 的固定轮询，在双核 runner 上超时，
**同一个 commit 在 PR 分支上是绿的**。代价不是一次 flake：unit 步骤失败 →
**后续 15 个步骤全部 skipped** → #551 这个纯 Windows 的修复合入后，
Windows 端到端信号是零。

- 固定轮询换成**带截止时间**的等待（30s，`XLINGS_TEST_WAIT_MS` 可覆盖），
  超时时打印任务的实际状态而不是只说「不相等」；
- unit 步骤改 `continue-on-error`，**结论在 job 末尾重新断言** ——
  红的 job 带完整信号，好过红的 job 什么都没有。

## 7. 兼容性

- **无 schema bump。** 唯一的格式变化是放宽（`runtime` 可缺席）与新增
  （`described_*`），`schema_version` 仍是 1。
- **升级方向安全**：新 client 读旧块一切照旧。
- **降级方向不安全，说清楚**：旧 client 的 `validate_block` 会把「`runtime`
  缺席」判为 `RuntimeMalformed`，于是 `self doctor` 报块损坏，而它的 `--fix`
  会用**它自己那个年代的** `DEFAULT_RUNTIME` 重写 —— 正是本次要修的行为。
  不会崩溃、不会丢 `envs`，但一个诚实的「未知」会被降级回一个猜测。
  这是降级路径的代价，不是升级路径的；**写在这里是因为它没有测试覆盖，
  只有这段文字。**
- **一次 Describe 重建不再抹掉真实的 `created_at`**（`describe_block` 会把
  完整的创建记录带过去）—— 删掉一个事实和发明一个事实是同一个错的两面。
- **不改变任何已存在 subos 的 runtime。** `runtime_for` 的第 1 源仍然是块里
  已有的声明；真机上那两条假声明只会被**报出来**，不会被改写。
- **无新命令、无新标志。** 迁移走的是本来就在运行的三个入口。

**没有端到端断言的一条**：`RemoveOutcome::Partial` 分支在 Linux/macOS 上**不可达** ——
我们自己的树里没有东西能抵抗我们（`clear_readonly_` 总能把目录改回可写，
打开的 fd 不阻止 unlink）。所以那条分支不做端到端断言，只对它落点的
`settle_removal` 用真实残留驱动。**声称覆盖了它才是假的绿。**

## 9. 改后在真机上的实测

read-only（不带 `--fix`），2026.8.17.1 的二进制对着那台 39-subos 的真实 home：

| subos | 声明 | sysroot | 新 finding |
|---|---|---|---|
| `mcpp-test` | glibc@2.44 | 2.39 | ⚠ **runtime drift** |
| `agent-influence` | glibc@2.44 | 2.39 | ⚠ **runtime drift** |
| `default` | glibc@2.39 | 2.39 | 静默 |
| `gfxbuild` | glibc@2.39 | 2.39 | 静默 |
| `agent-other-p` | glibc@2.44 | 2.44 | 静默 |

```
⚠ subos runtime drift  subos 'mcpp-test' declares runtime glibc@2.44, but
                       lib/libc.so.6 points into glibc@2.39 -- a binary built
                       here links against glibc@2.39, not against glibc@2.44
```

**两个方向都量到了**：命中的正是 §2 里从数据推出的那两个（含 issue #547 里那个
`mcpp-test`），一致的三个一条都没报。一个只会报警的检查和一个只会沉默的检查，
在只测一边的时候长得一样。

这两条**不会被 `--fix` 改写**（§3），因为哪一边是意外这里判断不了 ——
它们现在是可见的，而在此之前，`lib/libc.so.6` 那条符号链接摆在那里，
没有一行代码看过它。
