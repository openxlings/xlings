## 3. 分项

### 3.1 【A · P0】入口二进制:`self update` 升的是包,不是入口

**实测**:`$XLINGS_HOME/bin/xlings` 是 `local:xlings@0.4.51` 的字节级拷贝(6 月的载荷),
而 `xlings info xim:xlings` 说 `2026.8.11.1`。**每一个 shim 都经这个入口派发**,
于是整台机器的工具链行为退回到 6 月 —— 症状出现在三层之外
(`ld: cannot find crt1.o`),看起来像工具链缺少库搜索路径。

**为什么会长期不一致**:`self update` 升级 `xim:xlings` **包**;`bin/xlings` 是
**另一份拷贝**,没有任何东西对账。本次 `self update` 还因 `xim:` 与 `local:` 二义
而拒绝(确定性契约,行为正确)——**结果是没人升级入口**。

**要做**

1. `xlings self doctor` 增加一条检查。**判据不是「入口版本 ≠ 包版本」** ——
   自审时否掉了那个写法:一个 home 里可以合法地装着多个 xlings,`xim:` 与 `local:`
   两个命名空间都提供它(这正是 `self update` 拒绝的原因),所以「包版本」本身就是
   二义的,拿它当基准会得到一个二义的检查。

   **改成无歧义的方向性判据**:home 里存在**比入口更新**的已装 xlings ⇒ 报。
   它不需要回答「应该是哪一个」,只回答「入口落后了」,而这恰好是会咬人的那一半。
   用户有意钉住旧入口的情况不会被误报为错误(报 Notice 不报 Error)。

2. **命名空间优先级:`xim` > `local`,而不是二义即失败。**

   今天 `self update` 因为 `xim:xlings` 与 `local:xlings` 同时存在而拒绝 —— 行为符合
   确定性契约,但**结果是没人升级入口**,正是这次事故的一环。

   **拒绝是「没有规则」时的正确做法,不是「可以有规则」时的**。这里可以有规则:

   * **未限定命名空间**的目标(`xlings install foo` / `self update`)按**声明的优先级**
     解析,`local` **排在最后**。理由:`local:` 是本地旁路/开发用的旁支,实测这台机器上
     那份是 **6 月的实验残留**;而 `xim` 是维护中的通道。
   * **显式限定的目标**(`xlings install local:foo`)不受影响 —— 优先级只在
     「用户没说是哪个」时起作用。
   * 被降权时**多打印一行**,而不是静默:
     `local:xlings@0.4.51 也提供该名字,已按命名空间优先级选用 xim:;要选它请显式写 local:xlings@0.4.51`

   这不违反确定性契约 —— **它把「不确定」变成「有声明的确定」**,并且把差异说出来。
2. `self update` 在因二义拒绝之后,**不得静默继续**。今天的输出是
   「refuse … 然后 `[xlings] installing xlings@latest...`」——拒绝之后又装了一次,
   两句话互相矛盾。
3. 入口与包的关系写进 `graphics-stack-spec` 之外的一处规范(`AGENTS.md` 的排查段):
   **排查任何 shim 行为异常,先看 `$XLINGS_HOME/bin/xlings --version`。**

**判据**:把入口换成旧版 ⇒ doctor 必须报;换回 ⇒ 必须不报。

### 3.2 【A · P0】隔离契约有两套,而只有一套被写在所有地方

`self install` 与 `quick_install` **不认 `XLINGS_HOME`,只认 `HOME`**。
仓库里其余所有隔离都靠 `XLINGS_HOME`,于是任何「设了 `XLINGS_HOME` 就以为安全」
的验证步骤会直接写用户真实的 home。

**记录在案的次数:2026-07-30、2026-08-01、2026-08-11 —— 三次。**
前两次的处理都是「写进 memory,提醒自己小心」,而**产品行为没变**,所以有了第三次。

**要做**:二选一,不要第三条路。

自审否掉了「让 `self install` 尊重 `XLINGS_HOME`」这个选项:有些用户把
`XLINGS_HOME` 长期设在 shell 里,改语义会让他们的 `self install` 突然装到别处 ——
**用一个静默的错误换另一个静默的错误**。

**改成:说出来,并在两者冲突时拒绝。**

* `self install` **显式打印它将要写的目标目录**,不埋在进度条里(memory 记的
  2026-07-30 那次,失败之所以静默,就是因为这一行被淹没了)
* `XLINGS_HOME` 已设、且**与即将写入的目标不一致**时 ⇒ **拒绝并说明**:
  「本命令按 `HOME` 定位安装目标(`<目标>`),而 `XLINGS_HOME` 指向 `<另一个>`。
  要装到后者请设置 `HOME`。」

冲突才拒绝,不冲突照常 —— **零 blast radius**,而踩坑的那条路被堵死。

**判据**:`XLINGS_HOME=/tmp/x xlings self install` ⇒ 非零退出,且真实 home 的
`bin/xlings` 的 mtime 与内容**不得变化**;`XLINGS_HOME` 未设或一致时 ⇒ 照常安装。

### 3.3 【A · P0】未展开的标记被降级成空值,而不是错误

gcc 的 alias 是 `gcc --sysroot=${XLINGS_DYNAMIC_SUBOS_DIR}`(索引 #463,2026-08-06)。
旧派发者不展开它,标记原样落到 **shell**,shell 把未设置的变量展开成**空**:

```
COLLECT_GCC_OPTIONS='--sysroot=' ...
```

**空的 `--sysroot=` 比标记字面量更坏**:字面量会让 gcc 明确报错,空值让它**静默退回宿主**。
自包含性无声丢失,五天没人发现。

**要做**

1. shim 在把 alias 交给执行层之前扫描残留的标记 —— **但只认 `${XLINGS_*}`,
   不是任意 `${...}`**。自审时收窄了这一条:一个 recipe 完全可以在 alias 里
   故意写一个要交给 shell 展开的变量,把所有 `${...}` 一律拦下会把合法用法打死。
   **只对 xlings 自己字典里的名字负责**,这也正是 #463 注释立的分工。

   命中即**报错并说明**(「这个 alias 需要 xlings ≥ X 才能展开;当前入口是 Y」),
   而不是交给 shell。
2. `expand_subos_placeholder` 的空 `subos_dir` 分支同理:今天它**原样返回**,
   等于把标记交给下游。要么展开,要么失败,不要第三种。

**判据**:构造一个带未知标记的 alias ⇒ 必须报错;正常标记 ⇒ 必须展开。
两条都要,只有前者会退化成「永远报错」。

> **写法上的一条**:包装器/alias 里引用可选变量一律用 `${VAR:+ -flag "$VAR"}` —— 
> **没有值时整段消失,而不是变成空值**。上面这一整节就是空值与「没有」被混为一谈的代价。

### 3.4 【B · P1】`.wiring` 记录 provenance

记录由 `graphics` 的 config hook 写,内容却是**关于别的包的**(mesa / libglvnd /
nvidia-gl-host-link)。那些包升级时没有任何机制让它失效。实测物证:记录写于
`01:37:17`,它所描述的 nvidia 载荷写于 `01:38:14` —— **记录比它描述的东西早 57 秒**。

dispatch 那一层已经有失效机制(`dispatchMismatch` ⇒ `stale wiring`),**vendor 那一层没有**。

**要做(必须读写成对,一次做完)**

自审时发现原写法有个坑:「盘上版本与记录不符」**读取方答不出来** ——
它不能在查询时解析索引(即时查询契约),所以不知道某个 vendor 现在的版本是什么。
一条读取方无法评估的判据,就是一条不会生效的判据。

**改成读取方本地就能判的形式**:

* 写入侧(xim-pkgindex):每条 vendor 记 `payload=<载荷目录>`(绝对路径,含版本段)
* 读取方(xlings)**只做本地对照**:`glx-vendor/` 里那条符号链接的目标,
  是否仍然落在记录里的 `payload=` 目录之下?**不在 ⇒ `stale`**。
  vendor 包升级会重写符号链接指向新版本目录,而 graphics 的记录不会跟着变 ——
  这正是要抓的那一幕,而且**不需要问索引**。
* **向前兼容**:旧记录没有 `payload=` ⇒ **不报 stale**(没有观测,不产出判定)

EGL/GLES vendor 不在 `glx-vendor/` 里(它们经 JSON 发现),对这几条改用
「记录里的 `payload=` 目录是否仍然存在且仍含该 soname」—— 同样是本地判据。

**不要只做读取侧** —— 给一个没人写的字段先加解析器,正是本仓库
`closure_lib_paths()` 那条老毛病。

### 3.5 【C · P1】E2b:`ld` 包装器,分两步

在修好的环境上,#532 的两条**逐字复现**:

| | 链接 | 运行 |
|---|---|---|
| 只用 libc | ✅ | ✅ |
| `-lz`(farm 里的库) | ✅ | ❌ `libz.so.1: cannot open shared object file` |
| `-lGL`(自己还有跨载荷 DT_NEEDED) | ❌ | — |

产物 RUNPATH 只有 `glibc` 与 `gcc` 两个载荷;`libz.so.1` 就在 `<subos>/lib`。
**链接期看得见、运行期看不见** —— 这个不对称本身就是缺陷的形状。

**放在哪:binutils 载荷里,不单独成包。** 三条理由,前两条是硬的:

1. `binutils` 已经**独占注册** `ld`(`programs = { "ld", "as", "gold" }`)。另一个包再注册
   会撞上 2026.8.1.1 的**contested-name veto**;要么被否决,要么两个包抢一个 shim ——
   而「一个问题多个回答方」正是上一轮在治的病。
2. 包装器要知道「真的 `ld` 在哪」。单独成包就得依赖 binutils 再解析它的 payload,
   **「真 ld 在哪」立刻有了第二个推导方**。
3. `gcc-specs-config` 是「单独一个包去改别人载荷」的先例,但它是**反面**先例 ——
   设计文档 §3.1 批的就是它,而它今天还在咬人(mcpp 那份 specs 里 ~60 条指向
   已删除沙箱的 rpath)。

**形态:静态文件,因为契约是环境变量。**

```
<binutils payload>/bin/ld        ← 包装器(静态,不含任何 home/subos 路径)
<binutils payload>/bin/ld.real   ← 真的 ld
```

```sh
#!/bin/sh
exec "$(dirname "$0")/ld.real" "$@" \
  ${XLINGS_SUBOS_LIB:+-rpath-link "$XLINGS_SUBOS_LIB"}
```

`XLINGS_SUBOS_LIB` 已随 2026.8.11.1 发布,所以包装器**不需要在装机时被改写** ——
没有共享可变状态,没有第二个 `ld` 的主人,`xlings use binutils <ver>` 照常工作。

**自审补两条实现约束**:

* **`$0` 要稳。** 包装器靠 `dirname "$0"` 找 `ld.real`;`ld` 在 PATH 上是 xvm 的 shim,
  shim 用**绝对路径**去执行载荷里的 `ld`,所以 `$0` 是载荷路径,成立。但这是个
  依赖调用方式的假设 —— 写成对符号链接也稳的形式,并在包装器里注释为什么。
* **Windows 没有这条路。** `#!/bin/sh` 的包装器在 Windows 上不成立,而 binutils
  在 Windows 也有载荷。要么这条能力显式声明为 POSIX-only(并让 Windows 保持现状),
  要么给 Windows 另写一份 —— **不能默认「反正一样」**。本轮建议前者,写清楚。

**分两步,不要一次做完**

| 步 | 追加 | 写进产物? | 需要 #540 谈完? |
|---|---|---|---|
| **1** | `-rpath-link <farm>` | **否**(纯链接期) | **不需要**,对 mcpp 无害 |
| 2 | `--disable-new-dtags` | 是(标签) | 否(mcpp 同向,后出现者胜) |
| 2 | `-rpath <farm>` | **是** | **需要**:`XLINGS_SUBOS_LD_PATHS=0` 声明式退出 |

第 1 步单独就修掉 `gcc -lGL` 链不上,可以马上做。

**判据**:用户零 flag 下 `gcc -lGL` 链接通过(第 1 步);`gcc -lz && ./a.out` 跑通
(第 2 步);`XLINGS_SUBOS_LD_PATHS=0` 时产物**不含**任何 store 绝对路径而标签仍是 RPATH。

### 3.7 【D · P2】`<subos>/lib` 里无人管理的条目

#541 ③ 在 xlings 侧已证伪(`use` 确实重放 placement)。真实形态是
**recipe 的 config() 直接创建了 xvm 不管理的符号链接**,`use` 不可能重指它不知道的东西。
xlings 侧缺的是可观测性:**没有任何检查发现 farm 里存在无人管理的条目**。

**要做**:doctor 增加 `unmanaged farm entry`。**先做出可复现的样本再写守卫** ——
上一轮就是因为「这台机器上 nvidia 根本没有注册记录,做了也验证不了」而推迟的。

**自审补一条兼容性**:「farm 里有、ledger 里没有」在老 home 上会大量命中(旧客户端
写的条目本来就没有 placement 记录)。和 `installation_state` 同一个纪律:
**要正证据,不要缺证据**。可用的正证据是 —— 该条目指向的载荷**本身有 placement
记录、但这一条没有**;或者干脆等 3.4 的 provenance 落地后一起做。
否则会重演「115 个误报淹掉 29 个真报」。

### 3.8 【已在本方案内结案】E1a 迁移:不做全量重打,证据不支持

原来的说法是「已装可执行文件 17 DT_RPATH / 24 DT_RUNPATH,那 24 个拿不到 GPU」。
**那个数字是抽样得来的,而且结论是错的。** 全量量过之后:

```
form-X 可执行文件      DT_RPATH  29     DT_RUNPATH 144
DT_RUNPATH 总数        177
其中 DT_NEEDED 里有 libGL / libEGL / libGLES / libX11 / libwayland / libvulkan 的
                       0
```

**177 个里,零个链接任何图形库。** 那 144 个 form-X + DT_RUNPATH 的是什么?

```
llvm(33) binutils(18) gcc×4(68) glibc(11) cmake(5)
node×5(5) nvim ollama openssl alsa-lib(各 1)
```

**全是工具链和命令行工具。** 标签的传递性只在**深层 `dlopen`** 时起作用 ——
`gcc`、`ld`、`node`、`cmake` 不会去 `dlopen` 一个 GL vendor。所以「144 个拿不到 GPU」
这句话对**这些**二进制没有意义。

#### 但这个测量本身不充分,必须说清楚

设计文档 §7 早就写过:

> 判据(「需不需要传递标签」)**在二进制上看不见** —— 真实 GL 程序的 `dlopen` 引用数是 **0**,
> 是 `libGLX.so.0` 在调

所以「DT_NEEDED 里没有 libGL」**不能证明**它不是 GL 消费者 —— 一个程序完全可以在运行期
`dlopen`。我的测量只能排除**链接期就声明了图形依赖**的那一类。

**这恰恰是不做全量重打的理由,不是做的理由**:既然成员资格在二进制上看不见,
那么「把所有 form-X 都重打一遍」并不是一个有判据的动作 —— 它无法验收,
**做完之后没有任何测量能说明它有没有用**。这与 #534 是同一种错误:
**一个听起来吓人的数字,量在了错误的人群上。**

#### 结论:三条,取代原来的「全量重打」

1. **新装的已经是对的。** elfpatch 自 libxpkg 0.0.57 起写 DT_RPATH,`closure_check`
   rule E 在装机时验证。**这条链子不需要迁移,它已经闭合。**
2. **不做全量重打。** 144 个工具链二进制重装,代价是几百 MB 下载与一次全量 hook 重跑,
   而收益**无法被任何判据测量**。
3. **改成按需、可发现、可修**:标签不对的表现是**具体某个 GL 程序在软件渲染**,
   而那条通道已经存在 —— `subos info` 会说
   「ok for installed programs — but a program you build here cannot load it」。
   用户遇到时,`xlings install <该包>` 就是修法(经唯一写入者 elfpatch),
   doctor 的修复梯子已经会给出这条命令。

> **这条从「欠账」改判为「不是欠账」。** 留在方案里不是待办,是**结论**:
> 谁要重新提出全量迁移,得先拿出一个能验收它的判据 —— 而按设计文档 §7,
> 那个判据在二进制上看不见。

**如果将来真要做**,唯一有判据的形态是**声明式的**:让需要传递标签的包
**自己声明**(recipe 里一个字段),而不是让工具去猜。那时迁移集合是有限、可枚举、
可验收的 —— 那才是一个能排期的任务。

### 3.9 【E · P2】`remove` 不带版本仍打 active

本轮只改了**提示**(让它说出要带版本)。目标解析没动:不带版本时打的是 active,
而在触发那些错误的每一种情形里,active 都**不是**要清的那个版本。

**要做**:二选一 —— 清该包全部版本,或在有多个版本时**拒绝并列出**(与
`install` 的确定性契约一致)。倾向后者。

### 3.10 【E · P2】`egl-device` 无 DISPLAY 那一格

从未在 DT_RPATH 消费者下测过。按 harness 自己的规矩(`not-measured` 一律算失败),
这一格现在是**未知**,不是「坏」。**重测之前不许写根因。**

```
3.2 隔离契约 ─┼─→ 这三条互不依赖,且都是「让分叉可见」,一起做收益最大

3.5 步骤2 (-rpath + 退出) 需要 #540 谈定退出形态

```

**关键顺序**:3.1 要在 3.5 之前 —— 否则构建侧的任何验收都可能在一个派发者已经过期的
机器上做,得到的结论不可信。**这一轮已经因此浪费了一次。**

| | 为什么 |
|---|---|
| `ld` 包装器单独成包 | §3.5:抢 `ld` 名字会被 contested-name veto;且「真 ld 在哪」多一个推导方 |

## 6.5 方案自审:这一遍改了什么

写完之后按「每条判据能不能被评估、每条改动的 blast radius、老 home 会怎样」过了一遍,
六条被改写,记在这里而不是悄悄改掉:

| 原写法 | 问题 | 改成 |
|---|---|---|
| 3.1 比对「入口版本 ≠ 包版本」 | 「包版本」本身二义(`xim:`/`local:` 都提供 xlings,这正是 `self update` 拒绝的原因)⇒ 判据也二义 | 方向性判据:**home 里有比入口更新的已装 xlings ⇒ 报** |
| 3.2 让 `self install` 尊重 `XLINGS_HOME` | 有人长期把它设在 shell 里,改语义会让他们装到别处 —— **用一个静默错误换另一个** | **只在冲突时拒绝**,并显式打印目标目录。零 blast radius |
| 3.3 扫描残留的 `${...}` | 会打死「recipe 故意留给 shell 展开」的合法用法 | **只认 `${XLINGS_*}`**,只对自己的字典负责 |
| 3.4 「盘上版本与记录不符」 | **读取方答不出来** —— 它不能在查询时解析索引 | 改成本地对照:符号链接目标是否仍在记录的 `payload=` 之下 |
| 3.7 「farm 有、ledger 没有」 | 老 home 上会大量误报,重演「115 淹掉 29」 | 同 `installation_state` 的纪律:**要正证据**,或等 3.4 落地后一起做 |
| 3.8 E1a 迁移 | 没定「重装」还是「直接 patchelf」就排期 | **先定路线再排期**;倾向重装(经唯一写入者),但要先量代价 |

| 3.1 二义即拒绝 | 拒绝是「没有规则」时才对;这里**可以有规则**,而拒绝的结果是没人升级入口 | `xim` > `local` 的**声明式优先级** + 多打印一行,显式限定不受影响 |
| 3.8 「24 个拿不到 GPU」 | **抽样得来的数字,且量在错误的人群上** —— 全量 177 个 DT_RUNPATH 里**零个**碰图形 | **结案:不做全量重打**。要重开须先给出能验收它的判据 |

另外给 3.5 补了两条实现约束(`$0` 的稳定性、Windows 没有 `#!/bin/sh` 这条路)。

**这一遍最值得记的一条**:上面六条里有四条(3.1 / 3.4 / 3.7 / 3.8)是同一种毛病 ——
**我写了一条「听起来对」的判据,但没有问「谁来评估它、他手上有没有那个信息」**。
`.wiring` 那条尤其典型:读取方**按契约就不该查索引**,所以一条要求它知道版本的判据,
落地那天才会发现做不了。**判据必须连同「谁在什么时候用什么信息评估它」一起写。**

## 7. 边界

* **一台机器,一种硬件**(NVIDIA / X11 / x86_64)。E5 的跨硬件覆盖仍未做。
* **`bin/xlings` 是什么时候、被哪一步换掉的,没有查清**。时间落在会话窗口内,
  我不把它推给别处;但具体是哪个命令写的,我没有证据,也不猜。
* **gcc 16.1.0 的内置 `--with-sysroot` 指向构建机的一个工程 subos** ——
  已查清并**提为 xim-pkgindex#604**,本轮**不处理**。

  不是 specs 的问题(specs 里没有 `--sysroot`),是编译期配置值固化进了二进制。
  **alias 的动态渲染是对的、而且生效**:经 shim 时 `-print-sysroot` 正确;
  只有**绕过 shim** 的调用(构建系统把编译器缓存成绝对路径)才会拿到那个外部路径。
  形态上仍是「一个决定两个来源」,但**不阻塞**:mcpp 侧自己生成 specs 与构建参数,
  不依赖这个配置;普通用户路径都经 shim。判据已写进 issue,可进索引 CI。

  **不要和 §3.1 混为一谈**:§3.1 是「派发者版本过旧」,这条是「即使派发者正确,
  绕过它就拿到别人的 sysroot」。
