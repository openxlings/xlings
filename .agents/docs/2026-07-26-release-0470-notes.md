## 一句话

**`xlings use` 现在要么把整个工具链发布版本切换到位，要么什么都不改并说明原因。**

在此之前它可能把 `gcc` 切到 15、把 `g++` 留在 16、把头文件留在第三个版本上，而且不报任何错。

## 用户可见的变化

### 修复

| 变化 | 之前 |
|---|---|
| `xlings use` 切换整个发布版本 | 只切换入口 target，其余成员留在原处 |
| 从任一成员进入结果一致 | 从 `gcc` 和从 `g++` 进入可能得到不同结果 |
| 切换失败时磁盘零改动 | 中途失败留下 sysroot 与 workspace 互相矛盾 |
| 删除后整组一致回退 | 逐 target 独立挑选，可能 `gcc` 用 GCC 而 `g++` 用 musl |
| 删除后幸存版本的头文件被放回 | sysroot 可能一个头文件都不剩 |
| 安装非激活版本不再覆盖 sysroot | 覆盖了 active 版本的头文件，且 `use` 修不回来 |
| 状态文件原子替换 | 写入中断会**清空** `~/.xlings.json`（整个版本库）或用户的 `~/.bashrc` |
| `install`/`remove`/`use` 互斥 | 并发运行时后写的抹掉先写的 |
| 失败时给出 code 与可执行 hint | 只有一句 `install failed` |
| `self doctor` 能看见 binding 状态 | 只看 shim 和 payload |
| `self doctor --fix` 可停用不一致的发布 | 无法处理 |

### 行为变化（可能被感知为倒退）

**一批过去静默通过的操作现在会明确失败。** 这是有意的 —— 它们此前在静默地损坏状态。

| 情况 | 现在 |
|---|---|
| 同一 exact `(target, version)` 已被别的包拥有 | 拒绝安装，提示先卸载拥有它的包 |
| recipe 声明 headers 但无法判定归属 | 拒绝安装，提示在 header 上指定 group |
| 无版本的删除且存在多个匹配 | 拒绝，要求给出带 namespace 的完整版本 |

每一条都带稳定的 `code` 与一条 hint。发布前已对钉住的官方索引做过审计：**113 个 recipe、89 个使用 xvm，零拒绝**。

其它变化：

- 指向状态文件的**硬链接不再跟随更新**（原子替换换掉了 inode，这正是安全性的来源）
- 在**不可写目录**中改写已存在的状态文件现在会失败（暂存文件需要在该目录创建）
- `XLINGS_NO_LOCK=1` 可绕过状态锁（仅用于诊断卡住的锁，会告警）

## 升级

**`xlings self update` 即可，无需任何手工步骤。**

- 0.4.69 的 `~/.xlings.json` 直接可读，**无格式迁移**
- 已有 shim 继续工作，不需要重建
- 升级前激活的工具链，升级后仍然激活且版本不变
- **回滚到 0.4.69 是安全的** —— 本版本未改变磁盘格式

---

## 已知限制

诚实列出，不以"可恢复"一笔带过。

| 限制 | 影响 | 计划 |
|---|---|---|
| **元数据损坏的条目仍是死路** | 若 `~/.xlings.json` 中某条目的 `bindingGroup` 字段畸形，`use` 会拒绝，而 `doctor --fix` 修不了它 —— 需要手工编辑 `versions.json` | 0.4.71 |
| `use` 的文件系统副作用非事务 | 决策已与执行分离，失败不再半切换；但提交点之后的文件系统操作仍非原子 | 0.4.71 |
| 无物化台账 | 无法识别 sysroot 中不属于任何包的文件 | 0.4.71 |
| `profile rollback` 不覆盖 xvm 状态 | 回滚不会还原激活的工具链 | 0.4.71 |

**元数据损坏的自救方式**：`xlings self doctor` 会打印出错条目与精确到字段的 JSON Pointer
（例如 `/bindingGroup/rootVersion`），据此手工编辑 `~/.xlings.json` 后即可恢复。

## 内部变化（不影响使用）

- 存储格式仍是 #384 的 root-manifest 形态。group 归一化为顶层表推迟到 0.4.71，
  届时需要一个兼容读窗口（详见 plan §0.15 的决策与代价记录）。
- 六个 CI workflow 现在也在 `release/**` 分支上运行。
- CI 不再在恢复 mcpp 缓存后立即删除其中的 payload —— 此前每次运行都必须重新从各上游
  主机拉取全部传递依赖，任何一个不可达就全线失败。
