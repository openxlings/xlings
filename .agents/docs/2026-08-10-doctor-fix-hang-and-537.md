# `self doctor --fix` 为什么像卡死,以及 #537 的判定条件缺失

> 两个问题,一个共同的形状:**一个正确的判断,在错误的假设下被呈现。**
> doctor 假设用户能等 145 秒而不需要知道它在做什么;`.wiring` 假设自己的判定不依赖
> 消费者是谁。两者都不是恶性 bug,都是"说出来的东西与实际情况不匹配"。
>
> 实测环境:真实 home,124 个载荷 / 71 GB,xlings 2026.8.10.4。

## 一、`self doctor --fix` 卡住

### 1.1 实测

| 命令 | 耗时 |
|---|---|
| `self doctor` | **0.75 s** |
| `self doctor --fix --dry-run`(隐含 `--deep`,**不做任何修复**) | **148 s** |

输出的时间分布是决定性的:

```
[xlings] deep audit scope: all installed payloads     ← t=0 立刻打印
        ↓  145 秒,零输出
  ◆ xlings self doctor                                ← 结果一次性涌出
```

**37 行输出里,最长的静默间隔是 145 秒,就在那句"要审计全部已安装载荷"之后。**

而这还只是 `--dry-run`。真正的 `--fix` 在这之后还要重装两个 codex 载荷,**每个 336–350 MB**。

### 1.2 时间花在哪

`--fix` **隐含 `--deep`**(`spec.cppm`:`{"--fix", "Repair (implies --deep)"}`)。深审计枚举
store 里**每个包 × 每个版本**,对每一个跑 `elfcheck::scan_payload` —— 一次完整的 ELF 遍历:

```
124 个载荷目录 / 71 GB  →  145 秒
```

这个代价**与 home 的体量成正比**,而且**每次 `--fix` 都要全额支付**,哪怕要修的只是
两个坏载荷。

### 1.3 三个各自独立的问题

**A. 沉默。** 145 秒没有任何进度。用户无法区分"在扫描"、"卡在网络上"、"死了"。
这个仓库反复出现的形态在这里换了个方向:通常是**失败长得像成功**,这次是
**工作长得像卡死**。

**B. 范围与目的不匹配。** `--fix` 要修的是 doctor 已经点名的那几个 finding。
为此扫描**全部 124 个载荷**,是用一个与问题规模无关的成本去解决一个已知规模的问题。
只读 doctor 用 0.75 秒就已经知道要修哪四个。

**C. `--fix` 隐含 `--deep` 这件事没有出口。** 用户想修那四个 finding,没有办法说
"就修它们,别扫 71 GB"。`--scope` 存在,但它是给审计用的,不是给修复用的。

### 1.4 优化方案

**D1 —— 进度必须出来(必做,最小)**

深审计逐载荷推进时报告进度。判据:**145 秒内不得有超过 ~2 秒的静默**。
形式可以是覆盖式单行(`[47/124] xim-x-codex@0.144.1`),与安装进度同源。

这一条不改变任何行为,只是让"在工作"与"卡死"可区分。**它是其余各条的前提** ——
在能看见进度之前,任何性能优化都无法被用户感知为改善。

**D2 —— `--fix` 不应无条件全量深扫(核心)**

`--fix` 的输入是**已知的 finding 列表**。深审计的作用是**发现新 finding**,这两件事
在 `--fix` 场景下不必耦合:

- 默认:`--fix` 只审计**与待修 finding 相关的载荷**,其余不扫
- 想要"边修边全量体检"的用户显式写 `--fix --deep`

预期:本机从 148 秒降到**与 finding 数量成正比**(4 个载荷,亚秒级)。

风险:`--fix` 可能因此**漏修**深扫才能发现的问题。这是真实的取舍,不是纯收益 ——
所以默认值必须在输出里说清楚:"只审计了 4 个相关载荷;`--deep` 扫描全部 124 个"。
**沉默地缩小范围,是把一个慢问题换成一个静默正确性问题**,那更糟。

**D3 —— 深扫结果可缓存(可选)**

`elfcheck::scan_payload` 的输入是载荷目录,而载荷是**不可变**的(store 语义)。
同一个 `<包>@<版本>` 的扫描结果在它被重装之前不会变。按载荷缓存(键:路径 + mtime),
第二次 `--deep` 只扫新增/变更的载荷。

这条与 D2 正交:D2 减少**要扫的载荷数**,D3 减少**重复扫描**。

**D4 —— 网络阶段同样要有进度**

`--fix` 的 R2/R3 shell out 到 `xlings install`。普通 CLI 下子进程输出可见,但
**在 agent/protocol 模式下 `platform::exec` 会附加 `>/dev/null 2>&1` 把子进程完全静音**
(`platform.cppm:229`)。所以同一个命令在 agent 下会是**真正的零输出**,时长还要加上
700 MB 的下载。

至少要在 shell out 前后各报一句"正在重装 X@Y(约 N MB)"。

### 1.5 优先级

| | 项 | 收益 | 风险 |
|---|---|---|---|
| **P0** | D1 进度 | 把"卡死"变成"在工作" | 无 |
| **P0** | D2 `--fix` 范围收敛 | 148 s → 亚秒 | 有:必须显式说明缩小了范围 |
| P1 | D4 网络阶段进度 | agent 模式下的零输出 | 无 |
| P2 | D3 载荷级缓存 | 全量 `--deep` 提速 | 缓存失效判据要对 |

**先做 D1。** 在能看见进度之前,没人能判断 D2 是否真的改善了体验。

## 二、#537:`.wiring` 的判定缺一个条件

### 2.1 实测

同一个 home、同一个 interposer、同一台机器,**只改消费者的 ELF 标签**:

| 消费者标签 | `libEGL_nvidia.so.0` | `libGLESv2_nvidia.so.2` | 真实渲染 egl / gles2 |
|---|---|---|---|
| DT_RUNPATH | 打不开 | 打不开 | llvmpipe |
| **DT_RPATH** | **LOADED** | **LOADED** | **NVIDIA** |

而 `.wiring` 记录说 `nvidia EGL state=broken reason=runpath-not-transitive`,面板照此显示。

### 2.2 为什么

`graphics.vendor_closure_gaps` 判的是 **interposer 孤立看**的可达性:它带 DT_RUNPATH,
所以它背后的宿主驱动够不到我们的载荷。**孤立看是对的。**

但加载器的规则是:**消费者的 DT_RPATH 是传递的**。一个正确打标签的可执行文件打开这个
interposer 时,消费者的搜索路径对整条链都在作用域内,`libpthread.so.0` 因此可解析。

**所以这个判定以消费者的标签为条件,而记录格式没有表达这个条件。**

libxpkg 0.0.57 之前,几乎所有已安装可执行文件都是 DT_RUNPATH,**这个判定在事实上是
准确的**。0.0.57 之后已安装程序都是 DT_RPATH —— 判定不再准确,而记录不知道自己的
前提变了。

### 2.3 为什么这比"报错"更值得修

**低报比高报隐蔽。** 一个报"坏"却其实能用的检查,会

1. 派人去修一个不存在的问题(今天派了我几个小时,试了三种"修法"全是负收益);
2. 掩盖真正还坏着的那部分(用户自己构建的程序确实拿不到 GPU —— #532);
3. 让 `subos info` 这条**唯一的通道**开始说不准确的话,而它的全部价值就是准确。

### 2.4 方案

**E1 —— 判定要表达它的条件(推荐)**

把 `broken reason=runpath-not-transitive` 拆成两种状态:

| state | 含义 | 面板 |
|---|---|---|
| `ok` | 任何消费者都能用 | ok |
| `needs-transitive-consumer` | 打了 DT_RPATH 的消费者可用;DT_RUNPATH 的不可用 | 「已安装程序可用;你自己构建的程序不可用 → #532」 |
| `broken` | 任何消费者都不可用 | BROKEN |

好处:面板说的话对两类程序都准确,而且它**顺带把 #532 的影响面告诉了用户**——
那正是他们唯一会真实遇到的症状。

**E2 —— 探测时用带 DT_RPATH 的探针**

即模拟一个正确打标签的消费者,得到"已安装程序会看到什么"。更简单,但它**丢掉了
用户自建程序的那一半信息**,而那一半现在是真实存在的缺口。

**倾向 E1。** 它多说一句话,换来的是面板对两类消费者都不撒谎。

### 2.5 对账工具的盲区(必须一起修)

`graphics-acceptance.sh` 报"记录与加载器一致" —— 因为**它自己的探针也是默认 dtags 编的**,
复现的正是记录描述的那个失败。

这是这个工具踩过两次的同一个坑的**第三种形态**:

> **测量工具与被测对象共享同一个错误假设时,它们会一致地错。**

修法:**两种标签各测一遍**,像 `matrix.sh` 的 tag differential 那样。两者不一致,
就是 `needs-transitive-consumer`。

## 三、两者的共同形状

doctor 的沉默和 `.wiring` 的低报,都不是逻辑错误 —— 两处的**计算都是对的**。
错的是**呈现所依赖的前提**:

- doctor 假设"用户能等,不必知道在做什么" —— 在 71 GB 的 home 上这个前提破了
- `.wiring` 假设"这个判定不依赖谁来打开它" —— 在 0.0.57 之后这个前提破了

**前提变了而结论没变,产生的不是报错,是一句不再为真的话。** 这类问题不会被测试抓到,
因为测试通常和实现共享同一个前提 —— §2.5 的对账工具就是活例。
