# 2026.9.5.1 —— 「不是问路径在不在,是问 payload 在不在」

> 设计:`2026-09-06-relocated-home-doctor-design.md`
> 追加分析:`2026-09-06-issue-583-followup-analysis.md`
> 被推翻的判断:`2026-09-06-doctor-blind-spots-and-honest-verdict-plan.md` §1 表格最后两行、
> `2026-09-06-issue-583-relocation-design.md`(当天作废,当晚被实测推翻)
> 基线:2026.9.4.1(`8bfa8fa`)
> 来源 issue: #583(报告者第三轮回复)

## 1. 一句话

`self doctor --fix` 有两个破坏性动作 —— 删 sysroot 链接、注销注册 —— 它们**只问过
「记录里的路径存在吗」,从来没问过「payload 在当前根下吗」**。

在一个被 `mv` 过的真实 home 上(152 GB / 97 subos / 2908 条记录),这个差别是:

```
2026.9.4.1:  42 秒,删 1173 条 sysroot 链接、注销 367 条注册
             data/xpkgs 下 234 个包目录一个没少
             每条注销都说 "its payload is gone and nothing can restore it"
```

两个断言都是假的:payload 在;`xlings install xz@5.8.3` **1.25 秒**就把它恢复了,不下载。

## 2. 这不是「支持搬家」

`mv` 一个 home 仍然**不受支持,也不会变成受支持** —— `PT_INTERP` 由内核按字面读、
`$ORIGIN` 在那里不展开,linker script 里是绝对路径,payload 里的东西谁都改不回来。
这次改的是别的:

> **「不修」不等于「可以毁」。**

而且判据不是「这个 home 搬过家吗」,是**「这条记录指的 payload,在当前根下存在吗」** ——
后者不是搬家专属的状态:绑定挂载、容器内的不同挂载点、从备份恢复、父目录改名,
都会产生同一个状态。修的是一个**谓词问错了问题**,不是一个不被支持的操作。

## 3. 为什么当天白天判过「不做」,当晚又做了

当时的判据是「复现一个不被允许的操作造成的破坏,证明不了缺陷」,按它,
「拒绝注销新根下可达的载荷」被判为**不做**。推翻它的是三件当时没有量过的事:

| 新证据 | 数字 |
|---|---|
| 破坏的是**可恢复**的数据,而且代码自己写着相反的规则(`doctor.cpp:2464`:*"Deletion is what you do when nothing can say where the link belongs, not when you have not asked"*) | 1173 条链接 + 367 条注册,payload 全在 |
| 给出的**理由是假话** | `its payload is gone` —— 恢复只要 1.25 秒且不下载 |
| **2026.9.4.1 让这个场景比 2026.8.30.2 更糟**:把 `lib/` 加进扫描(修盲区)之后,原本只是"悬空"的链接被删掉了 | 8.30.2 上一条 symlink 就能全恢复;9.4.1 之后不能 |
| doctor **自己的不收敛护栏**在这种 home 上触发,对照组不触发 | 移动后 350 → 603 issues;未移动同一命令收敛正常 |

一个工具在合法操作之后报「这是 doctor 的 bug,请上报」,那就是 doctor 的 bug。

## 5. 修了什么

| # | 缺陷 | 位置 |
|---|---|---|
| **B1** | 两个破坏性动作从不在当前根上验证 payload。现在共用一个谓词,并且**先重指、后判死** | `doctor.cpp` `sysroot_link_source_` / `prune_dead_registrations_` |
| **B2** | `its payload is gone and nothing can restore it` 对着在盘上的 payload 说 | 同上,现在改为 `kept … its payload is present at <路径>` |
| **B3** | 损失口径只认注册剪枝,删 sysroot 文件仍报 `OK` / exit 0 | `RepairReport::removedAssets` 进三档判决 |
| **B4** | `--fix --dry-run` 不调用 `repair_local_`,预览漏掉全部破坏性动作;并且用过去时描述没发生的事 | `dryRun` 变成 `repair_local_` 的一个**模式**,不是另一个预测它的函数 |
| **B5** | 只有「链接悬空」没有「链接该在却不在」,所以旧客户端删掉的链接**事后不可见** | 新 `FindingKind::SysrootMissing` + 重新放置 |
| **B6** | 没有任何东西说出「这个 home 被移动了」 | 新 `FindingKind::HomeRelocated`,一条 finding 代替几百条症状 |
| **B7** | `xvm-sysroot-drift` 用**链接文本**前缀判归属,可解析的 home 被判 302 条、`--fix` 后 601 条 | 两边都 canonicalize;`SysrootEntry::linkTarget` 的契约写进接口 |
| **B8** | `library_placement`/`file_placement` 直接读 `path`,不过 `expand_path`,与 doctor 的读法不一致 | 加**必填**的 `xlingsHome` 参数(默认参数会把分歧保留下来) |
| **B9** | 只读 home 上同一条件重复报 3 次 | 渲染前按 (label, text) 去重 |
| **B10** | 索引缓存存的是**绝对**配方路径,搬家后目录扫不到任何包 —— 修复阶梯问「这条能重装吗」得到的全是 no,剪枝接手 | 一起重指;并在重指后强制重建 catalog、清空 probe 缓存 |
| **B11** | 自审查出的:`Config::versions()` **合并**全局与 project 两个作用域,project 的记录名的是 `<checkout>/.xlings`,在文本上与"搬过家"完全同形;同一个包通常两边都有,可恢复性判定也会满足 —— 会把 project 的载荷路径重指进全局 store | 判定追加一条:旧根必须**已经不存在**,或者**解析到本 home**(老路径 symlink 那个 workaround) |
| **B12** | 一条事实被复述成几百条:411 broken payload + 1173 悬空链接 + 304 drift,每条还各自给一个**对它错误**的补救 | 症状归入那一条 finding;**被压下去的必须被数出来**,link 数直接写进 finding 那行 |

## 6. 实测(全部在本机,`.agents/tools/slice-real-home.sh` 切片,每轮 `verify-untouched` = OK)

真实 home 切片(152 GB / 97 subos / 2908 条记录),`mv` 之后一次 `self doctor --fix`:

| | 2026.9.4.1 | 2026.9.5.1 |
|---|---|---|
| 删除 sysroot 链接 | **1173** | 24(= 未移动时的基线数) |
| 注销注册 | **367** | 见 §6.1 |
| 重指记录 | — | **2901** |
| 重指链接 | — | **1148,跨 95 个 subos** |
| 重指索引缓存 / subos 清单 | — | 1 / 1 |
| `self doctor` 的 broken payloads | 411 | **45**(= 基线) |
| `self doctor` 的 binding state | 304 | **2**(= 基线) |
| `self doctor` 的 warnings | 1173 | **25**(基线 24) |
| 报告里出现「moved/relocated」 | **0 次** | 1 条 finding,含旧路径、新路径、被重指的链接数 |
| `--fix` 之后 pruned / healed | 367 / 299 | **6 / 344**(未移动对照组:6 / 40 + 重指) |

搬过的 home 现在跟没搬过的 home **读起来一样**,多的只有一行解释:

```
✗ home relocated  this home is at <新>, but its records were written for <旧> —
                  2901 registration(s) still name the old path and 2606 of them
                  have their payload present here; 1148 sysroot link(s) point
                  into the old path and will be re-pointed
```

合成 home 三格矩阵(机制,e2e 每次跑):

| 格 | 状态 | 9.4.1 | 9.5.1 |
|---|---|---|---|
| A | 未移动 | 零破坏,exit 1 | 同上(无回归) |
| B | `mv` 之后 | 删 2 条链接 + 注销 1 条,**exit 0**,`the rest of the home is consistent` | **零破坏**,记录与链接重指 |
| C | `mv` + 老路径 symlink | 零破坏(链接不悬空,看不见问题) | 零破坏,**并且不再依赖那条 symlink** |

### 6.2 改写面(先量再改)

真实 home 的版本库里,**哪些字段真的带着 home 路径**:

| 字段 | 条数 |
|---|---|
| `path` | **2901** |
| `alias` | 26 |
| `envs.JAVA_HOME` / `envs.LD_LIBRARY_PATH` | 19 |

重指覆盖 `path` / `includedir` / `libdir` / `alias` / `envs`(后两者是**子串**替换 ——
alias 是命令行、env 值可能是列表,路径不在开头);`fileSrc` / `fileDst` 按契约是相对路径,
不碰;`bindingUnreadable`(解析不了而逐字保留的 JSON 文本)也不碰 —— 改写读不懂的东西
不是修复。子串替换必须落在**路径边界**上,`<root>-backup`、`<root>.bak` 不会被改写,
这两个目录恰好是搬 home 的人最常建的。

## 7. 明确不做

- 不让 home「天生可搬」。payload 内容(`PT_INTERP`/`RPATH`、linker script、
  `.xlings-resolution.json`)一律不动 —— 那是 payload 的内容,不是 xlings 的簿记。
- 不让修完的 home 看起来是干净的。`home relocated` 的 `note` 一行明说
  「用旧路径编译出来的东西不会因此能跑」,该重新 provision 的仍然要重新 provision。
- 不把 `${XLINGS_HOME}` 占位符写进版本库(70 处直接读 `path` 的调用需要先审计;
  B8 是它的前置,但这次不做迁移)。

## 8. 验收

`tests/e2e/doctor_relocated_home_test.sh`(E2E-99),六格,对 2026.9.4.1 在第一条断言即失败:

- R1 搬过的 home 被**命名**为搬过,并说出旧路径与「修不了什么」
- R2 `--fix` 零删除、零注销;记录与链接指向当前根
- R3 **payload 真的没了仍然剪枝** —— 谓词是「payload 在不在」,不是「搬过家没有」
- R4 `--dry-run` 列出真实运行会做的事,且一个字节都不改
- R5 缺失的声明链接被发现并放回
- R6 老路径 symlink 的 workaround 也被修好,记录不再依赖它

`tests/unit/test_relocation.cpp`:15 例,探测与翻译的纯逻辑 —— 「无可恢复载荷则拒绝判定」
(否则真空 home 的死记录永远删不掉)、「取众数而非最长公共前缀」、
「前缀必须落在路径边界」(`<root>-backup` 不许被改写)、分隔符与 Windows 大小写,
以及 B11 的两面:**活着的第二个 home 不算搬家**、**老路径 symlink 仍然算**。
