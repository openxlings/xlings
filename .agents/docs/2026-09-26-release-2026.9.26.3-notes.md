## 2. 真机验证（Linux，mirror=CN）

`xlings config --mirror CN` → `xlings update` → `xlings self update`，用时 26 秒，CN 镜像约 5.6 MB/s：

```
entry binary 2026.9.26.2 -> 2026.9.26.3
PATH:  xlings 2026.9.26.3 via ~/.xlings/subos/current/bin/xlings
entry: xlings 2026.9.26.3    marker: 1
symlink shims: 752, not resolving to entry: 0
self doctor: 升级前后的 finding 完全相同（exit 1 来自早已存在的问题），没有 outdated shim
```

驱动这次升级的是旧客户端 2026.9.26.2。POSIX 的 shim 是符号链接，所以不需要重新指向；本机也没有误报（30 多个 subos，doctor 耗时 4.8 秒）。

**转交和重新指向**（在 v615 里手工放一个带标记、内容不同的旧副本当作 `ninja`）：

```
$ XLINGS_HANDOFF_TRACE=1 ninja --version          # 在沙箱内
```

转交的目标是 subos 自己的 `xlings`，不是 `~/.xlings/bin/xlings`。这个现象**本版本没有修复**，已记为 **#617**：`subos new` 会在每个 subos 里建一个空的 `subos/` 目录，于是 `is_home_root` 把 subos 目录也当成了 home 根。本例结果仍然正确，因为那个 shim 就是指向 entry 的链接。

## 4. 只有 Windows CI 抓到的三件事

1. **测试脚本的 PowerShell 解析错误**：`"$why: …"` 被当成带作用域的变量，要写成 `${why}`。这是 E2E-120w 自己的问题。
2. **新建 subos 在 Windows 上从来没有 `xlings` shim**：`subos new`、fork、自动安装三处找的都是不带 `.exe` 的 `bin/xlings`。改为调用 `xlings_binary_in_home`，这个问题同样属于"一个问题多个回答者"。
3. **`self install` 复制了锁文件**：`self init` 现在持锁，执行过它的便携 home 里会留下 `.xlings.lock`，`self install` 又把它复制到自己正持有的目标锁上。Windows 拒绝复制；POSIX 上会**悄悄替换掉被 flock 的 inode**，CI 却是绿的。现在锁文件和 owner sidecar 永远不会被复制，也不会被删除。

E2E-01 里的 `copy failed: …portable_moved\subos` 和 "shim table … not rebuilt" 警告在 main 上就有。确认方式是用 `gh api …/jobs/<id>/logs` 取 main 的完整日志，**不是** `gh run view --log`，后者对那个 run 返回的是空内容，读起来就像"main 上没有这个问题"。

## 5. 没有验证到的

- **Windows 真机上的热路径开销**（设计 O1）：CI 只证明了功能正确，没有测量每次调用多出来的开销。
- **由旧客户端升级、已经坏掉的 Windows home**：要执行一次 `& "$env:USERPROFILE\.xlings\bin\xlings.exe" self init`。E2E-120w 的 S1/S2 用 CI 预装的 v2026.8.27.5 当作"旧版 binary"测过这条路径；没有在用户真机上验证过。
