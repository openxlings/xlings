# 2026.8.14.1 —— 「一次就够的事,和画错地方的边界」

> 方案与实测:`.agents/docs/2026-08-14-four-perf-and-output-defects-plan.md`
> (§7 记了**三条被推翻的判断**,§8 是端到端验证)

## 1. 一句话

用户报的四件事,底下是两个形状:

- **一次就够的事做了 N 次,或者根本不必做** —— 深度审计每遍 fork 15,008 个
  子进程读 56.54 GB,而 `--fix` 要跑八遍;48% 的字节花在**别人的 home** 上;
  一条「我故意没有 url」的声明被当成异常反复报警。
- **正确的动作,画错了边界** —— 锁画在整条命令上而不是它保护的读-改-写;
  一行日志画成三次 write 而不是一行。

## 2. 数字

真实 home(364 payload / 73 GB),`--deep` 只读、可反复量:

| | 改前 | 改后(热) |
|---|---|---|
| `self doctor --deep` 单遍 | **2m3.1s** | **3.0s** |
| `self doctor --fix` 全流程 | ~14 min(单遍 × 7) | **8.76s** |
| 每遍 patchelf 子进程 | 15,008 | **0** |
| 每遍 patchelf 读取字节 | 56.54 GB | 0 |

**输出逐字节相同。** 这比速度重要:

```
$ diff <(grep -v "auditing payloads" 改前.log) <(grep -v "auditing payloads" 改后.log)
*** IDENTICAL OUTPUT ***
```

## 3. 四件事各自修了什么

### 3.1 `doctor` 慢 + 「重复循环」

「循环」是**七遍完整审计**,每遍从 0 计数。

审计每个 ELF 只要两个字段(PT_INTERP、DT_RUNPATH/DT_RPATH),却 fork 两次
`patchelf`(经 shell,所以每次两个进程),而 patchelf 为读一个 header
**要把整个文件读进来**。13,729 个 ELF 里只有 **1,279** 个带 PT_INTERP ——
另外 12,450 个是共享库,被完整读一遍只为确认「这里没有答案」。

- 新模块 `xlings.core.elfread` 从 program header 表直接读这两个字段。
- **patchelf 不再是审计的依赖,变成了测试的对照组。** 这不只是快慢:
  `locate_patchelf` 返回空时 `scan_payload` 返回空 —— **一次「找不到工具」的扫描
  和一次「干净」的扫描输出完全相同**。这个坑一直藏在性能问题下面。
- `PayloadScanCache`(键 = install stamp + 目录 mtime)让多遍变便宜。
- 嵌套 store 剪枝:74 个,4,845 个 ELF / 26.93 GB。
- 进度行带遍次,「循环」的错觉消失。

**故意没做**:按阶段跳过审计。它更快,但它是一条**没有机制强制**的断言 ——
哪天某个阶段长出副作用,审计就看不见了。缓存不下这种断言:谁改了 payload,
谁的 key 就变,谁就被重扫。

### 3.2 第二条 `install` 「卡住」

它以 50ms 轮询 flock,**整整 30 秒不吭一声**,然后失败。

- 第一次失败**立刻**开口,并从 `.xlings.lock.owner` **旁文件**报出持有者
  (绝不写被 flock 的那个 inode —— 它的全部风险就是 inode 被替换),
  还会说这个进程是否还活着。
- 超时 30s → **10 分钟**,`XLINGS_LOCK_TIMEOUT` 可覆盖(`0` = 无限等)。
- 锁改到**索引加载之后**才取,两条装不相干包的 install 不再因为其中一条
  在拉索引而互相等待。

实测:

```
[xlings] waiting for another xlings to finish with this home (pid 2041759, `xlings install gcc`)
[xlings] still waiting for another xlings (pid 2041759, `xlings install gcc`) — 1s
...
```

> **升级须知(自动化/CI)**:默认等待时间从 30 秒变成 10 分钟。
> 对着终端的人这是对的 —— 等的通常是一次真实安装,而且现在每秒都在报告等谁。
> 但**期待「被锁挡住就快速失败」的脚本会因此阻塞更久**。
> 这类场景请显式设 `XLINGS_LOCK_TIMEOUT=<秒>`,不要依赖默认值。
>
> 这不是假想的:本仓库的 `home_config_lock_test.sh` 就是这样的脚本,
> 它隐式继承了默认值,于是这次改动让它从约 2 分钟变成 **2401 秒**,
> 每次 CI 多花 40 分钟。见方案 §9.4。

### 3.3 故意没有 payload 的包不再报警

`nvidia-gl-host-link`、`wsl-gl-host-link` 的版本条目就是 `["0.1.1"] = { }` ——
它们装的是**在宿主机上现建的符号链接**。每次安装都打
`[warn] skipping …: resource has neither url nor source`,把正确行为描述成问题。

`declares_no_download_source` 去问**配方**,而不是匹配 libxpkg 的错误串 ——
匹配那段文字等于把它的措辞变成 xlings 依赖的接口。真忘了写 url 的配方仍会被
下游三道检查抓到(payload 空 / programs 没注册 / 失败标记),那三道一个没动。

实测(删掉 payload 目录后的真安装):

```
[debug] nvidia-gl-host-link: no download source declared; install hooks only
```

### 3.4 Windows:换行乱、前面有莫名缩进

一行日志是**两三次 write,没有锁**,而下载 worker 线程和 200ms 的进度重绘
在写同一个终端。一帧落在前缀和消息之间,`[xlings] ` 就被留在别人那一行的开头。

- 一行 = 一次 write,在 `xlings.core.console` 的互斥下;续行对齐。
- **单一 sink**:所有终端写入走 `stdout` FILE*,不再有 `std::cout`。
  Windows 上这两者是**真的两个 sink**(MSVC 的 `std::print` 走 `WriteConsoleW`
  绕过 FILE* 缓冲)。
- 进度渲染器发现自己的光标记账被作废时**追加新帧而不是覆盖**日志。
- Windows 上 stdout 设为无缓冲:MSVC 没有行缓冲,stderr 无缓冲,
  所以 warn 会超到更早写的 info 前面。

> **D4(MSVC 缓冲那一半)仍未在 Windows 上实测**,判别实验见方案 §4.1。
> 但 O2/O4 即使 D4 不成立也无害 —— 单一 sink 和显式 flush 在任何平台上都是对的,
> 这就是它们先落地的原因。

## 4. 顺带

`mcpp-style-ref` 把 `.cppm` / `.cpp` 接口实现分离定为**推荐默认写法**,
带上实测理由(冷构建 2.16×、单次实现改动 12.4×)和搬运时会变的四件事 ——
其中两件编译器不会告诉你(隐式 `inline` 丢失、接口里留下用不到的 import)。

## 5. 没做的,以及为什么

**把下载和解压移出 home 锁。** 缝隙是真实存在的 —— 下载写的是 `runtimedir`
缓存,而且它已经有自己的 per-file 锁 —— 但这改变了两条并发 install 能观察到
什么,需要自己的事务模型和并发 e2e。本轮把它塞进来,是拿已经量准的四项收益
去赌一个没想清楚的模型。方案 §7.4 有完整推理。

用户报的「卡住」已经不靠它解决了。

## 6. 复查抓到的、测试没抓到的

- **测试自己的 bug**:`test_log_line.cpp` 第一版用 `freopen("/dev/tty")` 还原
  stdout。本机能过,**CI 没有 tty**,还原失败之后这个二进制里所有测试的输出
  都会写进临时文件,连 gtest 报告一起消失。改成 dup/dup2 保存原 fd。
- **无效的验证**:第一次测「空 url 包不再报警」时包已安装,循环在
  `node.alreadyInstalled` 就 `continue` 了,**根本没走到改动的那一行**。
  它「通过」了,而且什么都没证明。
- **描述了不存在设计的注释**:`elfread.cpp` 的 `FileView` 注释讲了一个带上限的
  整文件读取和一条大文件慢路径 —— 两者都不存在,每次读取都是精确范围。
  描述一个「考虑过但没建」的设计,比没有注释更坏。
- **两个缩进者**:downloader 的候选 URL 列表手写了 `"\n    "`,在日志层开始
  对齐续行之后就变成双重缩进。调用点删掉自己那一份。
