## 1. 一句话

#583 报的是「home 搬家之后全坏了」。**那个诉求没做,也不会做** ——
`mv` 一个 home 不是受支持的操作,而 `PT_INTERP` 由内核按字面量加载、不展开 `$ORIGIN`,
所以「天生可搬」只能做到一半,而一半比没有更危险。

真正修的是那份报告**在路上暴露出来的东西**,判据只有一条:

> **触发它的操作是不是受支持的。**
> 复现一个不被允许的操作造成的破坏,证明不了缺陷。

按这条筛下来,#583 里属于 xlings 的缺陷是 3 条,加上实现过程中量出来的 3 条。

## 3. 做了什么

| # | 缺陷 | 触发路径 |
|---|---|---|
| 1 | `self doctor --fix` 在只读 home 上 SIGABRT | 正常命令 + 正常环境 |
| 2 | 顶层 catch 覆盖不到 `self`/`subos`/`profile` | 同上,`subos new` 也 134 |
| 3 | prune 之后报 `OK` | 载荷真的没了,正是 prune 的设计场景 |
| 4 | `<subos>/lib` 不在断链扫描内;修复只会删 | 纯 `xlings install` |
| 5 | `broken payloads` 计入了 subos 层的问题 | 任何有 subos manifest 问题的 home |
| 6 | 权限错误被建议「去提 issue」 | (4) 扩大 catch 覆盖面之后才够得着 |

**退出码一处没动。** `issues()` 仍然把 `subos` 计入总数;prune 之后仍然是 0 ——
退出码回答的是「这个 home 还需不需要人处理」,不是「这次运行做了什么」。
把它变成非 0 等于把「丢了东西」和「坏了」混成一个信号,那正是本次要修的 bug 反过来一次。

## 4. 真机量到的

| 其中断链 | 6 |

| 切片上改后报的断链数 / 修复后剩余 | **2 / 0** |
| 真实 store 被修改的文件数(`verify-untouched`) | **0** |
| 真实 home active lib 条目 / 目标名冲突 | 95 / **0** |
| 单元测试 | 51/51 |

那 6 条断链的来源值得单独说:同一个 `xim-x-freetype@2.13.2`,在 7 个 subos 里
**4 个正确、3 个指向载荷里不存在的 `lib/x86_64-linux-musl/`**,而版本库里的记录一直是对的。
这是**注册变了、只有当时活跃的 subos 被刷新**的结果 —— 已单开 #586,
本次只修「看得见」和「修得对」,没修「不再产生」。

## 5. 被实测推翻的判断

计划里写错、实现时被数字纠正的有 6 条,记在
`2026-09-06-doctor-blind-spots-and-honest-verdict-plan.md` §7 与 §8。最值得记的两条:

1. **那几条 freetype 链接最后是被删除、不是重指的,而删除是对的** ——
   `libfreetype.so.6` 不在 `default` 的 workspace 里(非激活版本),
   非激活版本的库本来就不该出现在 sysroot。我的验收标准写错了,不是代码错。
2. **第二轮自查抓到的 4 条全在这次自己新写的代码里**,而且其中 3 条是同一个形状:
   **新加的保护自己制造了一个新的不可分辨状态**。S1 在打戳有了局部 catch 之后
   就不再证明任何事;打戳失败的提示落在面板外;取第一个匹配的来源。
   这次要修的 bug 类,在修它的过程中又出现了三次。
